확인된 사실만 적습니다. 추측은 **추측** 이라고 명시합니다.
출처 표기: `[bin]` 순정 드라이버 바이너리, `[xml]` 순정 드라이버 데이터 파일,

## 1. 전송 계층 [bin] — 확정

| 항목 | 값 |
|------|-----|
| Vendor ID | `0x19F5` |
| Product ID | `0xFE20`, `0xFED0`, `0xFEB1` 중 하나 |
| USB 인터페이스 | `MI_01` (컴포지트 인터페이스 1) |
| 장치 열기 | `CreateFileA(path, GENERIC_READ\|WRITE, SHARE_READ\|WRITE, OPEN_EXISTING, FILE_FLAG_OVERLAPPED)` |
| 쓰기 | `WriteFile` = **OUTPUT 리포트** |
| 읽기 | 비동기 `ReadFile` = **INPUT 리포트** |
| 버퍼 크기 | **65 바이트** (리포트 ID 1 + 페이로드 64) |
| HID 리포트 ID | 0 |

> **정정.** 이전 판에서 FEATURE 리포트라고 적었던 것은 틀렸습니다. 바이너리에
> `HidD_SetFeature` / `HidD_GetFeature` 문자열이 있어 그렇게 추정했지만, 정적 분석 결과
> 두 함수는 `GetProcAddress` 로 **주소만 받아 두고 한 번도 호출되지 않습니다**
> (전역 `0x5a1f98` / `0x5a1f94` 에 대한 참조가 저장 1회뿐). `CH375*` 8개 임포트도
> 호출 0건인 죽은 코드입니다.
>
> 실제 통신은 `WriteFile` / `ReadFile` 이며, 이는 WebHID 의 `sendReport` 와
> `inputreport` 이벤트에 그대로 대응합니다. 즉 **웹 드라이버가 순정 드라이버와 똑같은
> 일을 할 수 있습니다.**

HID API 는 장치 열거·식별에만 쓰입니다: `SetupDiGetClassDevsA` 로 HID 장치를 훑고
`HidD_GetAttributes` 로 VID/PID 를, `HidP_GetCaps` 로 리포트 길이를 읽습니다
(`0x45cfd1`: caps+4 → InputReportByteLength, caps+6 → OutputReportByteLength).

읽기 래퍼는 `ReadFile` 이 돌려준 버퍼의 **선두 리포트 ID 가 0이면 그 1바이트를 벗겨서**
호출자에게 넘깁니다 (`0x45d1e3`). 그래서 응답의 첫 바이트는 페이로드 첫 바이트입니다.

### 1.1 송수신 헬퍼는 두 개다 [bin] — 확정

프레임은 하나지만 헬퍼는 둘입니다. **읽기 명령은 전부 두 번째 헬퍼에 걸려 있습니다.**

| | `0x45a940` | `0x45ab50` |
|---|---|---|
| 쓰이는 곳 | 쓰기 명령 (ACK 확인) | **읽기 명령** |
| 체크섬 합산 | `payload[4..63]` (60바이트) | `payload[4..62]` (59바이트) |
| `WriteFile` 길이 | 65 | 64 |
| 첫 읽기 타임아웃 | 30 ms, 20회 재시도 | 50 ms |
| 실패 시 | `Sleep(100)` 후 재전송, 50 ms 읽기 | `Sleep(10)` 후 재전송 |
| 성공 판정 | `payload[0] == 0xAA` | 동일 |

`0x45ab50` 의 길이 인자가 64인 것은 문제가 되지 않습니다 — 쓰기 래퍼 `0x45d020` 이
`HidP_GetCaps` 로 얻은 OutputReportByteLength 보다 짧으면 그 길이까지 0으로 패딩합니다
(`0x45d057`–`0x45d07c`). 체크섬 범위가 1바이트 짧은 것도 무해합니다: 읽기 요청은
`payload[7]` 이후가 전부 0이라 두 계산 결과가 같습니다.

> `tools/bin/commands.py` 는 이제 두 헬퍼를 모두 훑습니다. 초판은 `0x45a940` 만 봤고,
> 그래서 명령 표에 **읽기 명령이 통째로 빠져 있었습니다.**

### 1.2 응답은 1바이트 당겨져 돌아온다 [bin] — 확정

두 헬퍼 모두 성공하면 **받은 65바이트를 호출자 버퍼에 그대로 덮어씁니다**
(`0x45aafc`, `0x45ad51`). 리포트 ID 는 §1 대로 벗겨져 있으므로:

```
송신:  buf[0]=리포트 ID  buf[1]=0x55  buf[2]=명령  buf[3]=미사용  buf[4]=체크섬
수신:  buf[0]=0xAA       buf[1]=명령   buf[2]=?     buf[3]=체크섬   buf[4]=길이
       └ payload[0]      └ payload[1]               └ payload[3]    └ payload[4]
```

즉 **수신 버퍼의 인덱스가 곧 payload 인덱스**입니다. 순정 드라이버가 응답을 다시 요청으로
재활용할 때 `movups [ebp-0x97], xmm0` 처럼 1바이트 밀어서 복사하는 이유가 이것입니다
(`0x429621`).

## 2. 패킷 프레임 [bin] — 확정

`WriteFile` 에 넘어가는 65바이트 버퍼:

```
[0]      HID 리포트 ID (0)
[1]      매직 0x55            (펌웨어 업데이트는 0x5F)
[2]      명령
[3]      미사용 (관찰된 모든 호출에서 0)
[4]      체크섬 = sum(buffer[5..64]) & 0xFF
[5..64]  데이터 60바이트
```

리포트 ID 를 뺀 페이로드(WebHID 가 다루는 단위) 기준:

```
payload[0]      매직 0x55
payload[1]      명령
payload[2]      미사용
payload[3]      체크섬 (payload[4..63] 의 8비트 합)
payload[4..63]  데이터
```

체크섬 근거: `0x45a9a5`–`0x45a9dc` 의 루프가 10회 × 6바이트 = 60바이트를
`esi+5` 부터 `esi+64` 까지 더한 뒤 `mov byte ptr [esi+4], bl` 로 저장합니다.

### 2.1 블록 전송 [bin] — 확정

대부분의 명령은 독립된 동작이 아니라 **펌웨어 블롭의 바이트 범위를 한 패킷당 56바이트씩
옮기는 것**입니다. `0x0b` 명령 생성기(`0x429130`)에서 확인했습니다.

```
payload[4]      이 청크의 길이 (0x38 = 56, 마지막 청크는 더 짧음)
payload[5..6]   블롭 내 오프셋, 리틀엔디언 16비트
payload[7]      미사용
payload[8..63]  청크 데이터
```

근거가 되는 코드:

```
mov word ptr [ebp-0x53], 0xb55   ; buffer[1..2] = 55 0b  (매직 + 명령)
mov cl, 0x38                      ; 청크 길이 56
cmp ebx, 6 / cmove eax, 0x30      ; 마지막(7번째) 청크만 48
al = ((ebx*8 - ebx) << 3)         ; = ebx * 56  → 오프셋 하위 바이트
mov byte [ebp-0x4e], al           ; buffer[6] = payload[5]
... >> 8 → buffer[7] = payload[6] ; 오프셋 상위 바이트
movups [ebp-0x4b] ...             ; buffer[9..64] = 56바이트 데이터
```

`0x0b` 전송은 56×6 + 48 = **384바이트**입니다. 여러 명령 생성기가 **128**까지 도는
루프를 갖고 있어 384 = 128 슬롯 × 3바이트로 깔끔하게 나뉩니다. 키 인덱스가 109까지
올라가므로 128 슬롯이면 전체 키 주소 공간을 덮습니다.

### 2.1.1 읽기도 같은 형식이다 [bin] [hw] — 확정

읽기 요청은 데이터 없이 길이와 오프셋만 채웁니다. 응답은 §1.2 의 자리 그대로 헤더를
되돌려주고 **`payload[8..63]` 에 데이터 56바이트**를 실어 옵니다 (쓰기가 데이터를 넣는
자리와 같습니다).

순정 드라이버는 응답이 에코한 오프셋을 **믿지 않고** 자기 커서에 복사합니다. 우리
`readBlock()` 도 그렇게 합니다 — 펌웨어가 헤더를 반올림하거나 패딩해도 블롭이 밀리지
않습니다.

청크 분할 (전부 정적 분석으로 확인, `chunkPlan()` 이 재현):

| 명령 | 청크 수 | 마지막 청크 | 합계 |
|------|---------|-------------|------|
| `0x05` | 1 | 32 | 32 |
| `0x07` | 14 (i=0..13) | 40 | 13×56 + 40 = 768 |
| `0x08` | 10 (i=0..9) | 8 | 9×56 + 8 = 512 |
| `0x0a` | 7 (i=0..6) | 48 | 6×56 + 48 = 384 |
| `0xa0` | 19 (i=0..18) | 16 | 18×56 + 16 = 1024 |
| `0xde` | 7 (i=0..6) | 48 | 384 |

|-----------|-----------|------|
| `0x428f00` (0x0b) | 0x190 = 400 | 384바이트 전송 |
| `0x42a3e0` (0xdd) | 0x190 = 400 | |

### 전송 절차 [bin]

송수신 헬퍼 `0x45a940` 이 모든 명령에 공통입니다:

1. 체크섬 계산 후 `buffer[4]` 에 기록
2. `Sleep(2)`
3. `WriteFile` 65바이트 — 실패하면 1회 재시도
4. `Sleep(2)`, 수신 버퍼 65바이트 0으로 초기화
5. `ReadFile` 65바이트, **타임아웃 30 ms**
6. **응답 `payload[0] == 0xAA` 이면 성공** (`cmp cl, 0xAA` at `0x45aa8b`)

`src/protocol/frame.ts` 에 구현되어 있습니다.

## 3. 명령 표 [bin] [hw]

명령 바이트는 **두 송수신 헬퍼**(§1.1)의 호출 지점에서 추출했습니다
(`python tools/bin/commands.py "<순정 드라이버>/Raven Driver.exe"`).
ms 열은 초기 스윕에서 빈 페이로드로 보냈을 때의 응답 시간입니다.

읽기와 쓰기는 대체로 **읽기 = 쓰기 − 1** 로 짝을 이룹니다.

| 명령 | 방향 | 크기 | 내용 | 함수 |
|------|------|------|------|------|
| `0x01` | — | — | **확정** 트랜잭션 시작. 모든 명령 함수가 이걸로 시작 | 전부 |
| `0x02` | — | — | **확정** 트랜잭션 종료·적용 | 전부 |
| **`0x03`** | **읽기** | **35 B** | **[fw]** 펌웨어 빌드 식별자 (§3.6). **순정은 보내지 않습니다** — 펌웨어에서 찾았습니다 | 없음 |
| `0x05` | 읽기 | 32 B | **확정** 전역 설정 (§4.8) | `0x429300`, `0x429560`, `0x428a30` |
| `0x06` | 쓰기 | 32 B | **확정** 전역 설정 (§4.8) | `0x429560`, `0x428a30` |
| `0x07` | 읽기 | 768 B | **확정** 키맵 2레이어 (256 × 3). 슬롯 매핑의 출처 (§4.6) | `0x427ac0`, `0x427f80` |
| `0x08` | 읽기 | 512 B | 128 × 4. 베이스 오프셋 인자 있음. 고급키 추정 | `0x426bf0` |
| `0x09` | 쓰기 | 768 B | 키맵 2레이어 | `0x427ac0`, `0x427f80` |
| `0x0a` | 읽기 | 384 B | 키맵 1레이어. **이 보드에서는 전부 0** (미할당 FN 레이어 추정) | `0x427590` |
| `0x0b` | 쓰기 | 384 B | 키맵 1레이어 (128 × 3) | `0x428f00` |
| `0x0d` | 쓰기 | 3584 B | 미확인 | `0x428440`, `0x429a60` |
| **`0xa0`** | **읽기** | **1024 B** | **확정** 키별 성능 설정 128 × 8 (§4.5) | `0x427120` |
| **`0xa1`** | **쓰기** | **1024 B** | **확정** 같은 블록. 19청크 순서까지 해독 (§4.5.5) | `0x42c390` |
| `0xa3` | 쓰기 | — | 조명. 미확인 | `0x429a60`, `0x42a740`, `0x42b560` |
| `0xa5` | 쓰기 | — | ⚠ 조명. 보드 상태 변경 확인 (24 ms) | 위와 같음 |
| `0xa7` | 쓰기 | — | ⚠ 조명. 보드 상태 변경 확인 (21 ms) | 위와 같음 |
| `0xa8` | — | — | **아날로그 테스트 모드 진입** — §3.2. 타이핑이 멈춥니다 | `0x429f20` |
| `0xa9` | — | — | **모드 해제** — §3.2. ⚠ 보정 표를 플래시에 씁니다 (§3.3) | `0x429f20` |
| **`0xaa`** | **읽기** | **512 B** | **[fw]** 보정 표 64 × 8 (§3.3). **순정은 보내지 않습니다** — 펌웨어에서 찾았습니다 | 없음 |
| `0xdd` | 쓰기 | 384 B | 키별 RGB 128 × 3 (54 ms) | `0x42a3e0` |
| `0xde` | 읽기 | 384 B | 같은 블록 읽기 | `0x428c20` |
| **`0xee`** | — | — | ⚠⚠ **공장 초기화** | `0x443540` |
| `0x5f` `0x06` | — | — | 펌웨어 업데이트 (`0x41ea70`, 매직이 다름) | `0x41ea70` |

> ⚠⚠ `0xee` 는 작업 코드 `0x0c` 에서 단독으로 나갑니다. 보낸 뒤 `Sleep(1000)` →
> `Sleep(5000)` 하고 전 블록을 다시 읽습니다 (§3.7). **프로버나 스윕에 절대 넣지
> 마세요.** `src/protocol/frame.ts` 에서 `COMMAND` 가 아니라 `DANGEROUS_COMMANDS` 에
> 따로 두어 `KNOWN_COMMANDS` 에 섞이지 않게 했습니다.

> 읽기 명령들은 요청에 데이터를 싣지 않으므로 읽기 전용으로 **보입니다.** 하드웨어에서
> 부작용을 확인하지는 않았기 때문에 `SAFE_COMMANDS` 에는 넣지 않았습니다 — 프로버는
> 여전히 ⚠ 로 표시합니다. 예외는 `0x03` 과 `0xaa` 로, 둘 다 **펌웨어에서 핸들러를 직접
> 읽어** 쓰는 경로가 없음을 확인했기 때문에 `SAFE_COMMANDS` 에 있습니다.

### 3.0 작업 코드 → 핸들러 [bin]

작업 디스패처는 `0x442f00` 입니다. UI 가 코드를 큐에 넣고 워커 스레드가 여기서 분기합니다.

| 코드 | 핸들러 | 하는 일 |

### 3.1 응답 형식 [hw] — 확정

**쓰기 명령의 응답은 요청의 에코입니다.** `payload[0]` 만 `0xAA` 로 바뀌고 나머지는 그대로
돌아옵니다.

> 이 서술은 **쓰기 명령에만** 맞습니다. 읽기 명령(§3 의 방향 열)은 같은 헤더에 데이터를
> 실어 옵니다 — §1.2, §2.1.1.

```
보냄:  55 a9 00 38 38 00 00 …
받음:  aa a9 00 38 38 00 00 …
```

그래서 지금까지 관찰한 "ACK" 는 전부 에코였고, **명령이 실제로 무엇을 했는지 알려주지
않습니다**. 초기 스윕에서 전부 ACK 가 돌아온 것도 이 때문입니다.

응답에는 명령 바이트가 `payload[1]` 에 실려 오므로, 요청과 응답을 짝짓는 조건은
`payload[0] == 0xAA && payload[1] == 보낸 명령` 입니다
(`src/protocol/frame.ts` 의 `isReplyTo()`).

### 3.2 `0xa0` 아날로그 키 이벤트 [bin] [hw] — 해독 완료

`0xa0` 로 시작하는 리포트는 **보드가 요청 없이 올려보내는 아날로그 키 이벤트**입니다.
순정 드라이버는 `0x42c8a0` 에 전용 폴링 루프를 갖고 있습니다 — **쓰기 없이**
`readReport(버퍼, 65, 타임아웃 10ms)` 만 하고 `payload[0] == 0xa0` 이면
`0x426050(payload[1], payload[2], payload[3])` 로 넘깁니다.

Esc / A / Space 를 각각 한 번씩 눌렀다 뗀 16개 샘플을 교차 검증해 필드를 확정했습니다.
**16비트 필드는 빅엔디언**입니다 (§2.1 의 블록 오프셋이 리틀엔디언인 것과 다릅니다).

| 오프셋 | 크기 | 의미 |
|--------|------|------|
| `[0]` | 1 | `0xa0` 이벤트 마커 |
| `[1]` | 1 | `0x10` = 16, 본문 길이 |
| `[3]` | 1 | **키 HID usage** (Esc `0x29`, A `0x04`, Space `0x2c`) — DB 와 같은 주소 체계 |
| `[4..5]` | 2 BE | **선형화 이동량 `travelRaw`, 0…800.** 펌웨어가 `(기준값 − 현재값) / 보정계수` 로 만들고 800 에서 자릅니다 (`0xe7ac`). 초판의 "키별 게인" 은 방향이 뒤집힌 표현 — 관측된 게인이 `1 / 보정계수` 였습니다 |
| `[6..7]` | 2 BE | **깊이, 0.02 mm 카운트** (0 = 안 눌림, 스위치 스트로크 = 바닥). `travelRaw` 를 스위치 종류별 곡선에 통과시킨 값. `[6]` 은 펌웨어가 항상 0 으로 씁니다 (`0xde16`) |
| `[8]` | 1 | 미상. 얕게 누를 땐 `[7]` 과 같고 바닥 근처에서 갈라짐 |
| `[9]` | 1 | **방향**: `0x01` 누르는 중, `0xff` 떼는 중 |
| `[10]` | 1 | **보정 상태 바이트** — 펌웨어가 그 키의 LED 를 빨강/주황으로 켤지 정하는 값 그 자체 (`0xdec2`). 순정 디버그 문자열이 `check_count` 라 부르지만 펌웨어는 여기에 아무것도 세지 않습니다. §3.3 |
| `[11..13]` | 3 | **보정 계수의 10진 세 자리** — 정수부, 소수 첫째, 소수 둘째 (`0xdeda`). 순정이 `"%d%d%d"` 로 이어 붙이는 이유가 이것이고, 미보정 키의 `062` 가 계수 0.62 입니다 |
| `[12..13]` | 2 | 위 세 자리 중 소수부 두 자리. 초판이 "키별 센서값" 으로 본 것 — P 와 `/` 가 값을 공유한 것은 두 키의 계수가 같았기 때문입니다 |
| `[14..15]` | 2 BE | **총 스트로크.** 항상 200 은 아닙니다 — 펌웨어가 스위치 종류별 표(`0x15e08`)에서 읽습니다 (`0xdd62`): 200 / 190 / 185 / 175 / 170 / 167. 지금까지 본 보드가 전부 4.00 mm 스위치였을 뿐입니다 |
| `[16..17]` | 2 BE | 현재 ADC 값. 누를수록 감소 |
| `[18..19]` | 2 BE | 키별 안 눌린 상태의 ADC 기준값 (Esc 1877, A 1964, Space 1902) |

핵심은 **`[6..7]` 이 설정에서 쓰는 것과 똑같은 0.02 mm 카운트 단위의 실제 깊이**라는
점입니다. `× 0.02` 가 안 눌림에서 정확히 0.00 mm, 바닥에서 정확히 4.00 mm 를 줍니다.

순정 드라이버의 표시 환산은 조금 다릅니다 (`0x42c9a1`–`0x42c9b6`):

```
표시값 = min(40, 깊이16 × 40 / (총스트로크 − 5))     ← 0.1 mm 단위 0..40
```

총 스트로크에서 5카운트(0.1 mm)를 빼고 나눕니다. 바닥 근처 여유 보정으로 보입니다 (추측).

`[4..5]` 는 ADC 델타에 비례하는 값이고 게인이 키마다 다릅니다 (Esc 1.151, A 1.371,
Space 1.135). 즉 `[4..5]` 는 자속에 선형이고 거리에는 비선형이며, `[7]` 이 그것을
선형화한 실제 이동량입니다. 홀 센서의 물리와 맞습니다.

**총 스트로크가 4.00 mm 로 확정**되었습니다. 이전에 3.5 mm 로 가정했던 값을 고쳤습니다.

#### 이 채널은 켜야 하고, 계속 켜 둬야 한다 [bin] [hw] — 확정

> 이전 판에는 "읽기 전용이며 아무것도 켤 필요가 없다" 고 적혀 있었습니다. **틀렸습니다.**
> 그때는 순정 드라이버가 같은 세션에서 이미 보드를 켜 둔 상태였습니다 — 자세한 내용은
> [findings.md](findings.md) §4 의 오류 #6.

명령 바이트를 상수로 넣지 않는 호출 지점이 딱 하나 있습니다 (`0x429f20`). 62바이트가
0으로 채워진 맨 패킷을 만들고, 명령 바이트만 UI 모드 플래그에서 뽑습니다:

```
0x429f40  cmp   dword [this+0x541fc], 0
0x429f47  mov   byte [buf+0], 0x55        ; magic
0x429f4b  sete  al
0x429f51  add   al, 0xa8                  ; 플래그 0 → 0xa9,  0 아님 → 0xa8
0x429f53  mov   byte [buf+1], al
```

그리고 이벤트 폴링 루프 `0x42c8a0` 의 꼬리가 이것을 **주기적으로 다시 보냅니다**:

```
0x42cb11  cmp   dword [this+0x83c], 7     ; ← 탭 7(성능)일 때만
0x42cb18  jne   skip
0x42cb1a  cmp   dword [this+0x541fc], 0
0x42cb21  je    skip
0x42cb70  cmp   eax, 0x76c                ; ← 마지막 전송에서 1900 ms 경과
0x42cb80  call  0x429f20
```

즉 스트림은 **명령으로 켜야 하고, 2초 안에 다시 켜지 않으면 펌웨어가 스스로 끕니다.**
재전송 루프가 성능 탭에서만 돈다는 점이 관찰된 증상과 정확히 맞습니다 — 보드를 막 꽂았을
때는 아무것도 오지 않다가, 순정 드라이버에서 성능 탭을 열면 그때부터 흐릅니다.

#### 어느 쪽이 켜기인가 — `0xa8` 이다 [hw] — 확정

정적 분석만으로는 갈리지 않았습니다. 플래그 기본값(0)에서 나가는 것이 `0xa9` 라 그쪽을
켜기로 추정했지만 **반대였습니다.** 하드웨어에서 확인한 것:

| 명령 | 하는 일 |
|------|---------|
| `0xa8` | 아날로그 테스트 모드 **진입**. 키 깊이 이벤트가 흐르고, **키 입력은 나가지 않습니다** |
| `0xa9` | 모드 **해제**. 타이핑이 정상으로 돌아옵니다 |

`SAFE_COMMANDS` 가 `0xa9` 를 포함하고 `0xa8` 을 제외하는 이유가 여기 있습니다 — `0xa8`
은 쓰지 않지만, `0xa9` 를 뒤따라 보내지 않으면 **키보드가 타이핑을 못 하는 상태로
남습니다.** 스윕이 몰래 해도 되는 일이 아닙니다.

#### 이 모드는 바닥 자성값을 보정한다 [hw] — 확정

`0xa8` 은 단순한 관찰 창구가 아닙니다. 이 모드에서 키를 **끝까지 누르면 그 키의 바닥
자성값이 보정됩니다** — 순정 드라이버 성능 탭의 캘리브레이션과 같은 동작입니다.
드라이버가 이 모드에서만 1.9초마다 갱신을 보내는 이유도 설명됩니다: 사용자가 키를 하나씩
바닥까지 누르는 동안 모드가 유지되어야 합니다.

> ⚠ 따라서 **모니터를 켜고 키를 바닥까지 누르는 것은 쓰기 동작입니다.** §3.2 의
> 기준 ADC(`payload[18..19]`)가 이때 바뀔 수 있고, 그러면 `fingerprints.ts` 의 수정자
> 식별표가 어긋납니다. 어긋나면 이벤트 탭에서 다시 연결하면 됩니다.

웹 드라이버의 `startMonitor` 는 시작할 때 `0xa8`, 1500 ms 마다 갱신, 정지할 때 `0xa9` 를
보냅니다. 새로고침·탭 닫기로 React 정리가 안 도는 경로까지 덮으려고 `pagehide` 에서도
해제합니다 — 타이핑 못 하는 키보드를 남기지 않는 것이 이 코드의 최우선 조건입니다.

#### 보정 상태 — 순정 드라이버가 본 것 [bin] [lang] — 정정됨

> **이 절은 한 번 틀렸습니다.** 순정 드라이버만 보고 "보정 상태는 이벤트에서 계산된다,
> ADC 진폭의 키별 누적 최댓값이다" 라고 적었는데, **펌웨어에는 그런 계산이 없습니다.**
> 실제 판정은 §3.3 입니다. 아래는 그 결론에 이르게 한 순정 쪽 증거와, 그것이 왜
> 거기까지밖에 못 갔는지를 남겨 둡니다 (findings.md 오류 #19).

펌웨어는 보정이 덜 된 키의 LED 를 **빨강 / 주황**으로 켭니다. 순정 드라이버도 같은 것을
화면에 표시하는데, **이를 위한 읽기 명령은 없습니다** — 아날로그 이벤트만 씁니다.

이벤트 폴링 루프 `0x42ca33` 이 표시용 UI 에 넘기는 것은 정확히 다섯 개입니다:

```
MUI::KeyboardCtrl::SetKeyCalibration(
    key_code,                              ; ebx        — payload[3]
    표시깊이 0..40,                         ; [ebp-0x5c] — §3.2 의 환산식
    payload[10],                           ; [ebp-0x60] — 실제로는 보정 상태 바이트
    센서값 정수,                            ; eax        — payload[11..13] = 계수 × 100
    payload[18..19] − payload[16..17])     ; esi        — ADC 진폭
```

`mui.dll` 의 `?SetKeyCalibration@KeyboardCtrl@MUI@@QAEXHHHHH@Z` (`0x1005eb60`) 는 저장만
하는데, 넷 중 하나만 다르게 다룹니다:

```
1005ebb5  mov    ecx, [edx + 0x74]      ; 지금까지의 최대값
1005ebbb  cmp    [ebp + 0x18], ecx      ; 이번 진폭과 비교
1005ebbe  mov    [edx + 0x68], eax      ; 0x68 ← 깊이        (덮어쓰기)
1005ebc4  cmovg  ecx, [ebp + 0x18]      ;
1005ebc8  mov    [edx + 0x6c], eax      ; 0x6c ← payload[10] (덮어쓰기)
1005ebce  mov    [edx + 0x70], eax      ; 0x70 ← 계수        (덮어쓰기)
1005ebd1  mov    [edx + 0x74], ecx      ; 0x74 ← max(이전, 진폭)  ★
```

언어 리소스가 사용자 쪽에서 같은 이야기를 합니다:

| id | 내용 |
|---|---|
| 626 | `그린/옐로우/레드` — 범례 |
| 632 / 633 / 634 | `레드` / `오렌지` / `옐로우` |
| 900 | `키가 보정되지 않았습니다. 재보정 버튼을 눌러…` |
| 1056 | `…키보드에 빨간 불·노란 불이 켜지면 눌러서 보정해야 하며…` **`각 키들이 녹색이 될 때까지 반복해서 키들을 누르세요`** |

**여기서 추론이 한 칸 미끄러졌습니다.** "반복해서 누르면 좋아진다" 는 누적 최댓값과
맞고 `[0x74]` 의 `cmovg` 와도 맞으니 색은 진폭의 함수일 것이다 — 그럴듯하지만, 같은
문장이 §3.3 의 실제 규칙(계수는 단조 증가하고, 커질 때마다 상태가 한 칸 올라간다)과도
똑같이 맞습니다. 순정 드라이버 안에서는 두 가설을 가를 수 없었습니다. 문턱값을 아무리
찾아도 안 나온 것이 신호였는데 — **애초에 문턱값이 없었기 때문입니다.**

가른 것은 펌웨어입니다 (§3.3).

#### 보정은 식별표를 깨뜨린다 [hw] — 관측

캘리브레이션을 **시작한 시점에 따라** 일부 키의 기준 ADC 가 달라지는 것이 관측되었습니다.
증상은 두 가지로 나타납니다:

- 연결되지 않은 센서 주소가 몇 개씩 검출됨 → 기준 ADC 가 허용 오차(±3) 밖으로 밀려서
  `matchFingerprint()` 가 아무것도 고르지 않은 경우
- 모니터가 **전혀 다른 키로 인식** → 밀린 값이 같은 센서값을 공유하는 **다른 키의**
  기준 ADC 에 더 가까워진 경우. `0x0805` 의 LCtrl 1880 / LShift 1888 은 8 밖에
  떨어져 있지 않으므로, 4 이상 밀리면 서로 뒤바뀝니다

즉 §3.2 의 식별 방식 자체가 보정에 취약합니다. 지문의 뒷부분(기준 ADC)이 보정 대상이고,
앞부분(센서값)만으로는 키가 유일하지 않기 때문입니다.

관측용으로 **센서 탭**을 두었습니다 (`src/tools/Sensors.tsx`): 키별 원시 ADC 를 전부
보여주고, 내장 식별표의 각 항목에 같은 센서값에서 관측된 기준 ADC 중 가장 가까운 값을
붙여 차이를 표시합니다. 짝짓기가 모호해지는 경우 — 관측값이 표의 다른 키에 더 가깝거나
같은 거리인 경우 — 는 **추측하지 않고 모호로 표시**합니다. 표를 잘못 갱신하면 잘못된
정체성이 그대로 굳기 때문입니다.

> 미확정: 보정된 값이 **어디에 저장되는가** (RAM 인지 플래시인지), 그리고 모드 진입만으로
> 값이 바뀌는지 아니면 바닥까지 누른 키만 바뀌는지. 후자는 한 키만 바닥까지 눌러 보고
> 나머지 키의 기준 ADC 가 그대로인지 보면 갈립니다 — 센서 탭의 표류 표가 그대로 답을
> 줍니다.
>
> 미확정: 기준 ADC 대신 **보정에 영향받지 않는 식별자**가 있는가. 없다면 수정자 식별은
> 근본적으로 사용자 연결에 의존해야 합니다.

#### `0xa8` 은 걸쇠다 — 한 번 보내면 유지된다 [hw] — 확정

하드웨어에서 확정된 최종 동작이고, 앞선 두 가지 서술을 정정합니다.

`0xa8` 은 **두 가지를 동시에** 합니다: 아날로그 보고를 켜고, 보드가 키보드로 동작하지 않는
테스트 모드에 진입합니다. **앞의 것만 걸쇠**입니다.

| 보낸 것 | 결과 |
|---|---|
| `0xa8` | 보고 켜짐(유지) + 테스트 모드 진입 → **타이핑 멈춤** |
| `0xa8` → `0xa9` | 보고는 켜진 채 유지, 모드만 빠져나옴 → **타이핑 정상 + 깊이 수신** |
| `0xa8` 반복 (1.5–1.9초 주기) | 모드를 붙잡아 둠 = **캘리브레이션.** 타이핑 멈춤, 끝까지 누른 키의 바닥 자성값 보정 |

즉 **두 동작은 모드를 얼마나 붙잡고 있느냐의 차이**입니다. 순정 드라이버가 1.9초 주기로
재전송하는 경로(`0x42cb80`)는 자기 아날로그 모드 플래그가 켜진 **캘리브레이션** 경로일 뿐인데,
그것을 일반 모니터링에 그대로 옮겨 쓴 것이 잘못이었습니다. 그 결과:

- 모니터를 켜면 타이핑이 멈췄습니다 → 반복 전송 때문
- 기준 ADC 와 센서값이 계속 바뀌었습니다 → 모니터링 중에 계속 재보정되고 있었기 때문.
  §3.2 의 표류 증상은 상당 부분 **우리가 만든 것**입니다

웹 드라이버는 이제 `armAnalogStream(link)` 이 `0xa8` 직후 `0xa9` 를 보내 모드를 빠져나오고,
`{ keepAlive: true }` 를 줄 때만 모드를 붙잡습니다 — 모니터 탭의 캘리브레이션 모드 전용입니다.

> 처음에는 "`0xa8` 한 번이면 타이핑도 유지된다" 로 적었는데 틀렸습니다. `0xa8` 만 보내면
> 모드에 들어간 채로 남아 타이핑이 멈춥니다. `0xa9` 를 뒤따라 보내야 합니다.

> `0x06` 의 `payload[15]` 플래그는 **필요하지 않았습니다.** 어떤 비트를 써도 `0xa8` 없이는
> 스트림이 흐르지 않고, `0xa8` 이 있으면 플래그 없이도 흐릅니다. 아래 절은 순정 드라이버가
> 탭 진입 때 무엇을 하는지의 기록으로 남겨 두지만, 스트림을 켜는 조건은 아닙니다.

#### 순정 드라이버가 성능 탭 진입 때 보내는 것 [bin] — 확정, 다만 스트림 조건은 아님

갓 연결한 보드는 `0xa8` 을 보내도 조용합니다. 한 번 캘리브레이션을 돌린 뒤에야 흐릅니다.
빠진 단계는 **설정 쓰기**이고, UI 의 탭 전환을 따라가면 나옵니다:

```
0x43933c  탭 7 진입 → 작업 코드 0x0e 를 큐에 넣는다
            mov dword [ebp-4], 0xe / call 0x41b460 / mov [esi+0x83c], edi
0x442f00  작업 디스패처: 0x0e → call 0x429560
0x429560  0x01 → 0x06 → Sleep(0x190 = 400 ms) → 0x02
```

`0x06` 패킷에서 실제로 채워지는 바이트는 네 개뿐입니다 (나머지는 memset 0):

| 오프셋 | 출처 |
|--------|------|
| `payload[12]` | `tick_rate` 등 UI 플래그 묶음 |
| `payload[13]` | `dead_zone` 관련 |
| `payload[14]` | 플래그 묶음 |
| **`payload[15]`** | bit 0–1 `perf_bottomrapidtrigger_mode`, **bit 2 `actuation_check`**, **bit 3 자석축 테스트**, bit 5 `debounce_level` |

아날로그 모드 플래그(`[this+0x541fc]`)가 켜져 있으면 `or bl, 0xc` (`0x42994e`) 로 **bit 2 와
3 을 함께** 강제합니다. 캘리브레이션을 한 번 돌리면 보드가 그 상태로 남고, 그래서 그
다음부터 우리 앱에서도 스트림이 흐르는 것입니다.

`0x06` 의 다른 호출부(`0x428a30`, 전역 설정 적용)는 **겹치지 않는 범위** `payload[16..24]`
를 쓰고 `[12..15]` 는 0으로 둡니다. 순정 드라이버에서 탭을 옮길 때마다 리포트 레이트가
초기화되지는 않으므로, 펌웨어는 이 필드들을 독립적으로 다루는 것으로 보입니다 — 즉
`payload[15]` 만 쓰는 것은 드라이버 자신이 하는 일이고 다른 설정을 덮는 것이 아닙니다.

> ⚠ 다만 그 **바이트 안의** bit 0–1 / 2 / 5 는 사용자 설정입니다. `0x0c` 를 쓰면 그
> 설정들이 꺼집니다. 순정 드라이버에서 설정을 다시 적용하면 복구됩니다. 그래서 웹
> 드라이버는 이것을 `startMonitor` 에 넣지 않고 **모니터 탭의 명시적 동작**으로 뒀습니다
> (`enableAnalogReport`).

> 미확정: bit 2 (`actuation_check`) 만으로 충분한지, bit 3 이 필요한지, 그리고 이 플래그가
> 재연결 후에도 유지되는지(플래시) 아니면 매번 써야 하는지(RAM).

#### 해결: `payload[2]` 가 수정자 비트마스크다 [bin] — 확정

지문은 애초에 필요하지 않았습니다. 순정 드라이버의 이벤트 해석 함수 `0x426050` 이
답입니다:

```
0x426053  eax = payload[1]
0x426058  cmp eax, 0x10            ; 키 이벤트
0x42605d  eax = payload[2]
0x426060  ecx = payload[3]         ; 기본 반환값 = usage
0x426063  if (eax == 0) return 0   ; 무시
0x426067  eax--
0x426068  if (eax > 0x7f) return ecx
0x42606d  eax = byte [0x426110 + eax]   ; 128칸 케이스 표
0x426074  jmp  [0x4260ec + eax*4]
          → 0xe0 0xe1 0xe2 0xe3 0xe4 0xe5 0xe6 0xe7, 기본은 usage 반환
0x4260d3  cmp eax, 0xf0            ; Fn 이벤트
0x4260da  return (payload[2] == 0xff) ? 0xff : 0
```

`0x426110` 의 128바이트를 뜯어 보면 기본값(8)이 아닌 칸이 딱 8개이고, 위치가
**0, 1, 3, 7, 15, 31, 63, 127** — 즉 `payload[2]` 가 **1, 2, 4, 8, 16, 32, 64, 128**
일 때입니다. 값은 순서대로 `0xe0`…`0xe7`.

**즉 `payload[2]` 는 HID 수정자 비트마스크입니다.** 표준 순서 그대로:

| `payload[2]` | 비트 | usage | 키 |
|--------------|------|-------|-----|
| `0x01` | 0 | `0xe0` | LCtrl |
| `0x02` | 1 | `0xe1` | LShift |
| `0x04` | 2 | `0xe2` | LAlt |
| `0x08` | 3 | `0xe3` | LWin (LGui) |
| `0x10` | 4 | `0xe4` | RCtrl |
| `0x20` | 5 | `0xe5` | RShift |
| `0x40` | 6 | `0xe6` | RAlt |
| `0x80` | 7 | `0xe7` | RGui (Raven61 에는 없음) |

그리고 `payload[1]` 은 길이가 아니라 **이벤트 종류**입니다: `0x10` = 키, `0xf0` = Fn
(이때 `payload[2] == 0xff`).

`parseKeyEvent()` 가 이대로 해석하되 한 곳만 다릅니다. 드라이버는 비트마스크를 무조건
우선하지만, 여기서는 **`payload[3]` 이 실제 usage 면 그쪽을 우선**합니다 — 수정자를 누른
채로 다른 키를 눌렀을 때 그 키가 수정자로 잘못 해석되는 것을 막습니다.

**결과: 61키 전부가 스스로 이름을 말합니다.** 캘리브레이션과 무관하게 식별되므로,
`fingerprints.ts` 는 폴백으로만 남습니다.

#### 센서값도 바뀐다 — 지문 방식은 성립하지 않는다 [hw] — 확정

한 걸음 더 나쁩니다. 표류하는 것은 기준 ADC 만이 아닙니다. **`payload[12..13]` 자체가
바뀝니다.** 관측된 사례:

- 표에서 LCtrl 은 `0x0805` / 1880 입니다
- 캘리브레이션 후, 실제 LCtrl 이 **`0x0806` / 1879** 로 보고했습니다
- `0x0806` 은 LAlt(1881) 의 센서값이고, 1879 는 1881 과 2 차이 — 허용 오차 ±3 안입니다
- 그래서 LCtrl 이 **LAlt 로 해석되었습니다.** 미해석이 아니라 오해석입니다

같은 세션에서 `0x0806` 아래 기준값이 **4개** 관측되었습니다 (그 센서값을 쓰는 키는 표상
2개). 캘리브레이션을 언제 시작했는지에 따라 값이 달라지므로, 한 세션에 보정 전·후 정체성이
섞여 쌓입니다.

**결론: `센서값 + 기준 ADC` 는 식별자가 될 수 없습니다.** 두 축이 모두 캘리브레이션
산출물이기 때문입니다. 숫자만 갱신해서 표를 고치는 것도 불가능합니다 — 위 예에서 갱신된
표는 LAlt 1880, 실제 LCtrl 1879 로 1 차이가 되어 애초에 구별이 안 됩니다.

그래서 두 가지를 했습니다:

1. **내장 식별표를 끌 수 있게** 했습니다 (`sensorMap.setIgnoreBuiltIn`). 표가 어긋난
   뒤에는 맞히지 못하는 것보다 **틀리게 맞히는 것이 더 나쁩니다.** 센서 탭이 어긋남을
   감지하면 (표에 없는 센서값, 또는 키 수보다 많은 기준값) 끄도록 안내합니다.
2. **주소가 될 바이트를 찾습니다.** usage 로 스스로 이름을 말하는 키들이 정답지이므로,
   바이트마다 "한 키 안에서 고정 + 키마다 다름" 을 검사할 수 있습니다. 센서 탭의
   *키 주소 후보* 패널이 그것이고, `payload[2]` / `[6]` / `[10]` / `[11]` / `[20..]` 이
   아직 해독되지 않은 자리입니다.

> 미확정: 그런 바이트가 실제로 존재하는가. 없다면 수정자 식별은 **사용자 연결이 유일한
> 방법**이며, 캘리브레이션 후에는 매번 다시 연결해야 합니다. 순정 드라이버가 같은 문제를
> 어떻게 푸는지도 아직 안 봤습니다 — 드라이버는 키 주소(`keyIndex`)로 설정을 쓰므로,
> 이벤트에서 키를 식별하는 자기만의 방법이 있어야 합니다.

`src/protocol/frame.ts` 의 `parseKeyEvent()` 가 디코딩하고, 코덱의 `startMonitor` 가
여기에 연결되어 **모니터 탭이 실제로 동작합니다**.

#### 키가 아닌 이벤트가 섞여 있다 [hw] — 관측

정상 동작하는 보드에서 지문 `0601:0` 이 계속 올라옵니다 — 센서값 `0x0601`, 기준 ADC `0`.
61키 전부가 제대로 보고되는 상태에서도 나오므로 키 이벤트가 아닙니다. 무엇인지는
미해독입니다.

기준 ADC 는 저장된 캘리브레이션 상수이므로 실제 키라면 0 일 수 없습니다. 따라서
`parseKeyEvent()` 는 **usage 도 수정자 비트도 없고 기준 ADC 도 0** 인 이벤트를
`identifiable: false` 로 표시하고, 키를 식별하는 쪽(모니터)은 이를 건너뜁니다. 어떤 방법으로도
식별될 수 없는 리포트를 "연결되지 않은 센서 주소" 로 경고하면, 사용자가 할 수 있는 일이 없는
경고가 됩니다. 센서 탭에서는 **키 아님** 으로 표시해 계속 보여 줍니다.

#### 수정자 키는 usage 대신 센서 주소로 식별한다 [hw] — 확정

61키 **전부** 아날로그 이벤트를 보냅니다. 다만 8개는 `payload[3]` 이 HID usage 가 아닙니다:

| 키 | `payload[3]` |
|----|--------------|
| LShift / RShift / LCtrl / RCtrl / Win / LAlt / RAlt | `0x00` |
| Fn | `0x01` |

HID 에서 수정자는 키코드 배열이 아니라 **첫 바이트의 비트마스크**로 보고되므로 키코드가
없고, 펌웨어는 그 자리에 `0x00` 을 넣습니다. Fn 은 레이어 키라 `0x01` 입니다. 수정자가
아닌 키(Menu `0x65`, Space `0x2c` 등)는 전부 정상적인 usage 를 보고합니다.

그래서 `payload[3]` 만으로는 7개 수정자를 서로 구별할 수 없습니다.

`payload[12..13]` 을 키별 센서 주소로 봤지만 **틀렸습니다** — P 와 `/` 가 같은 값을
씁니다. 주소가 아니라 캘리브레이션 곡선이나 게인 선택자로 보입니다 (추측).
`payload[18..19]` 기준 ADC 는 키마다 다르므로, 두 값을 **조합**해야 식별자가 됩니다.

웹 드라이버의 식별 순서:

1. `payload[3]` 이 `0x01` 초과면 HID usage 로 키를 찾는다 (53개 키)
2. 아니면 `센서값:기준ADC` 조합을 연결 표에서 찾는다 (수정자 7개 + Fn)

#### 확정된 식별표 [hw]

8개 전부 하드웨어에서 측정해 `src/keyboard/fingerprints.ts` 에 넣었습니다. 연결 작업
없이 바로 동작합니다.

| 키 | usage | 센서값 | 기준 ADC | 인덱스 |
|----|-------|--------|----------|--------|
| LShift | `0xe1` | `0x0805` | 1888 | 41 |
| RShift | `0xe5` | `0x0808` | 1927 | 52 |
| LCtrl | `0xe0` | `0x0805` | 1880 | 53 |
| LWin | `0xe3` | `0x0801` | 1827 | 54 |
| LAlt | `0xe2` | `0x0806` | 1881 | 55 |
| RAlt | `0xe6` | `0x0806` | 1898 | 57 |
| RCtrl | `0xe4` | `0x0809` | 1905 | 59 |
| Fn | `0xff` | `0x0801` | 1815 | 60 |

센서값이 겹치는 조합과 기준 ADC 간격:

| 센서값 | 공유하는 키 | 최소 간격 |
|--------|-------------|-----------|
| `0x0801` | Fn 1815, LWin 1827 | 12 |
| `0x0805` | LCtrl 1880, LShift 1888 | 8 |
| `0x0806` | Esc 1877, LAlt 1881, RAlt 1898 | 4 |
| `0x0808` | RShift 단독 | — |
| `0x0809` | RCtrl 단독 | — |

Esc 는 usage 로 해석되므로 `0x0806` 의 4 간격은 실제로 문제되지 않습니다. 식별표에서
가장 가까운 쌍은 LCtrl / LShift 의 **8** 이므로, 허용 오차를 **±3** 으로 두었습니다.
그보다 멀거나 두 후보가 정확히 등거리면 **엉뚱한 키를 고르지 않고 미해석으로 남깁니다**.

기준 ADC 는 저장된 캘리브레이션 상수입니다 (한 키의 모든 샘플에서 값이 동일했습니다).
보드에서 **재캘리브레이션을 하면 이 값이 바뀌어 식별표가 어긋날 수 있습니다.** 그때는
이벤트 탭에서 다시 연결하면 되고, 사용자 연결이 내장 표보다 우선합니다.

알려진 다른 센서값: Esc `0x0806`(기준 1877), A `0x0702`(1964), Space `0x0808`(1902).

> 초기에 `0xa9` 의 응답으로 봤던 `a0 10 00 08 …` 도 사실 이 이벤트였습니다.
> 웹 드라이버의 `request()` 가 내용과 무관하게 "다음 입력 리포트" 를 응답으로 삼았기
> 때문입니다. 지금은 `isReplyTo()` 로 응답과 이벤트를 구분합니다.

### 3.3 보정 표와 LED — `0xaa` 로 직접 읽는다 [fw] — 확정

출처가 새로 생겼습니다: **`[fw]` = 실제 키보드 펌웨어**. 순정 업데이터
`Raven FW/FW.exe` 안에 리소스 `BIN`/134 로 들어 있는 121584 바이트 RISC-V 이미지이고,
스스로를 `HALL_HS_USB_KB` (Nov 13 2024 11:05:59) 라고 부릅니다. 읽는 방법과 두 가지 함정은
[reverse-engineering.md](./reverse-engineering.md) §펌웨어, 아래 숫자를 이미지에서 다시
뽑아 보려면 `python tools/fw/calibration.py`.

#### 보정 레코드

펌웨어가 플래시 `0x20300` 에 **슬롯당 8바이트, 64개**를 들고 있습니다. 부팅 때
`0xa5aa` 가 RAM `0x20001b24` 로 통째로 읽고, 아날로그 모드를 나갈 때(`0xa9`) 다시
씁니다 (`0x14810`).

| 오프셋 | 크기 | 의미 |
|--------|------|------|
| `[0..3]` | float32 LE | **보정 계수 `scale`** — 전체 스트로크 1/800 당 ADC 카운트 |
| `[4]` | 1 | **상태 바이트** — LED 색을 정하는 값 |
| `[5..7]` | 3 | `AA BB FF` 태그. 없으면 부팅 때 레코드를 새로 씁니다 (`0xa5e8`) |

출고 기본값은 64개 전부 `52 b8 1e 3f  00  aa bb ff` — 계수 0.62, 상태 0.

계수가 보정의 실체입니다. 매 스캔마다 펌웨어는
`travelRaw = (기준 ADC − 현재 ADC) / scale` 을 계산해 800 에서 자르고 (`0xe7ac`),
스위치 종류별 곡선(`0x15e34`, 8종 × 201개 u16)에 통과시켜 이벤트의 깊이 카운트를
만듭니다. **즉 계수가 자석에서 밀리미터로 가는 환산 그 자체**이고, 계수가 틀린 키는
깊이를 틀리게 보고합니다.

#### 계수를 학습하는 규칙 (`0xe5d8`)

상태가 `0xFF` 가 아닌 키에 대해서만 돕니다:

```
cand = (기준 ADC − 현재 ADC) / 800.0                    ; 0x1569c
if (cand > scale && cand < 2.0 && cand − scale > 0.005)  ; 0x156a0, 0x156a4
    if (round(cand × 100) 이 24 스캔 연속 같으면)          ; 0x156a8, 0xe6ca
        scale = cand
        if (state <= 1) state++
```

**단조 증가만 합니다.** 지금까지보다 깊게 누르면 계수가 오르고, 내려가는 길은 초기화뿐입니다.

두 번째 증가 경로가 아날로그 테스트 모드 안에 하나 더 있습니다 (`0xf10a`):
`travelRaw >= 768` (`0x156b4`, 전체의 96 %) 이고 직전 값과 7 이상 차이 나며 계수가
0.63 (`0x156b8`) 을 넘으면 상태가 한 칸 오릅니다.

#### LED

상태 바이트로 팔레트 `0x1753c` 를 인덱싱하는 오버레이가 `0x13974` 에 있고, **상태가 1
이하일 때만 칠합니다**:

| 상태 | LED |
|------|-----|
| `0x00` | `#FF0000` 빨강 |
| `0x01` | `#FF8000` 주황 |
| `0x02`…`0xFE` | 칠하지 않음 (다음 스캔에 `0xFF` 로 넘어가는 과도 상태) |
| `0xFF` | 칠하지 않음 — 조명 효과가 그대로 보입니다 |

순정 드라이버가 말하는 "초록" 은 초록으로 칠하는 게 아니라 **덮어쓰기를 그만두는 것**입니다.

#### ⚠ 그래서 이 상태 바이트는 믿을 수 없다

상태는 품질이 아니라 **계수가 몇 번 커졌는지 센 값**이고, 두 번에서 포화합니다.
양방향으로 틀립니다:

- 모든 레코드가 상태 0 으로 출고되므로 **펌웨어를 새로 올린 직후에는 멀쩡한 키까지 전부
  빨강**입니다. 순정 문자열 1056 이 묘사하는 게 정확히 이 상황입니다.
- 계수가 0.005 만 커져도 한 칸 오르므로 **얕게 두 번만 눌러도 "보정됨"** 이 됩니다.
  바닥까지 눌렀는지와 무관합니다.
- 이미 계수가 맞는 키는 더 커질 수 없으므로 **영영 빨강**으로 남습니다.
- 부팅 검사(`0xa63a`)는 계수가 `[0.62, 1.24]` 를 벗어나면 계수를 0.62 로 되돌리면서
  **상태를 `0xFF` 로 박습니다** — 버리기로 한 레코드가 "보정됨" 으로 보고됩니다.

정직한 신호는 계수 쪽입니다. 바닥값 0.62 는 출고값이자 초기화값이자 부팅 검사의 하한이라,
**계수가 아직 0.62 인 키는 한 번도 보정된 적이 없는 키**입니다. 이 프로젝트는 이쪽으로
판정하고 (`src/protocol/calibration.ts`), 보드의 상태 바이트는 나란히 보여 주기만 합니다 —
둘이 어긋나는 지점이 쓸모 있는 정보이기 때문입니다.

> ⚠ 하나는 여전히 이 프로젝트가 정한 값입니다: "거의 보정 안 됨"(주황)과 "보정됨"을
> 가르는 `WEAK_HEADROOM`. 펌웨어에 대응하는 개념이 없어 베낄 것이 없었고, 펌웨어 자신의
> 0.63 선이 떨어지는 위치를 기준으로 잡았습니다. 바닥값과 상한은 펌웨어 상수 그대로입니다.

#### `0xaa` — 보정 표 읽기 [fw] — 확정, 하드웨어 검증됨

**순정 드라이버는 이 명령을 보내지 않습니다.** 펌웨어 쪽에서 찾았습니다: 명령 분배표
(`0x157b0`, `payload[1]` 로 인덱싱)의 `0xaa` 항목이 `0x711c` 로 가고, 그 핸들러는
플래시 `0x20300 + 오프셋` 에서 `payload[4]` 바이트를 읽어 `payload[8..]` 에 담는
**블록 읽기 그 자체**입니다. 베이스 주소가 핸들러 안의 상수라 다른 곳은 읽을 수 없고,
쓰는 경로가 없습니다.

요청 형식은 §2.1.1 의 블록 읽기와 완전히 같습니다. 56바이트 청크 9개와 8바이트 하나,
합쳐서 512바이트가 표 전체입니다 (`readCalTable`, `src/protocol/raven61.ts`).

**하드웨어 응답 [hw].** 리포트 콘솔에서 단독으로 보낸 결과, **5 ms 만에** 답했습니다:

```
aa aa 00 11 38 00 00 00 | d7 a3 50 3f ff aa bb ff | 7b 14 66 3f ff aa bb ff | …
ACK  cmd  ck len offset   scale=0.815  st tag       scale=0.89875 st tag
```

체크섬 `0x11` 은 `payload[4..64)` 합과 일치하고, 길이·오프셋이 요청 그대로 돌아오며,
56바이트에 8바이트 레코드가 정확히 7개 들어옵니다. **펌웨어에서 읽어낸 레이아웃이
바이트 단위로 맞았습니다** — float32 스케일, `state`, `AA BB FF` 태그 순서까지.

첫 청크 7개 레코드의 스케일은 0.815 / 0.89875 / 0.9575 / 0.89875 / 0.88875 / 0.835 /
0.8925 였고, **일곱 개 모두 `× 800` 이 정수입니다** (652, 719, 766, 719, 711, 668, 714).
학습식이 `cand = (rest - live) / 800` (`0xe5d8`) 이라면 저장된 값은 반드시 그래야 하므로,
분모 800도 데이터로 확인된 셈입니다.

> ⚠ **동시에 보내면 안 됩니다.** 이 명령이 처음에 "응답 없음" 으로 보였던 이유는
> 펌웨어가 아니라 호스트에 있었습니다. `0xaa` 와 키맵 읽기의 `0x01` 을 같은 밀리초에
> 쓰자 보드는 나중 것만 답했습니다 — HID 패킷 버퍼(`gp + 0x134`)가 하나뿐이라 앞 패킷이
> 덮인 것입니다. 지금은 `HidLink` 가 모든 쓰기를 직렬화합니다
> (`src/hid/link.ts`, 검사는 `tools/check/link-queue.ts`).
> 같은 이유로 `0xa8`(첫 진입 ACK 15.9 ms)과 `0xa9`(플래시 쓰기 ACK 34.5 ms) 직후에는
> **ACK 를 받고 나서** 다음 명령을 보내야 합니다.

한 가지 부수 효과를 기억해야 합니다: **`0xa9` 는 타이핑 복구만 하는 게 아니라 보정 표를
플래시에 씁니다** (`gp-0x72a` → `0x14810`). 캘리브레이션 패스가 저장되지 않으면 의미가
없으니 당연한 설계지만, `0xa9` 를 보내는 것은 그 패스가 학습한 것을 확정하는 일입니다.

#### 분배표 전체 [fw]

펌웨어가 실제로 처리하는 명령은 31개입니다 (나머지는 전부 `0x76ce`, 무시):

```
01 02 03 04 05 06 07 08 09 0a 0b 0c 0d
a0 a1 a2 a3 a4 a5 a6 a7 a8 a9 aa b0 b1 dd de ee f1 f2
```

`03` `04` `0c` `a2` `a4` `a6` `aa` `b0` `b1` `f1` `f2` 는 §3 의 명령 표에 없던 것들입니다.
지금까지 해독한 것은 `aa`(보정 표, §3.3)와 `03`(펌웨어 빌드 식별자, §3.6) 둘입니다.

`04` 는 읽으면서 같이 보였습니다: 핸들러(`0x74de`)가 플래시 `0x20000 + payload[5]` 에서
`payload[4]` 바이트를 `payload[8..]` 로 옮기는 블록 읽기입니다. 내용은 확인하지
않았지만 **주소로 이웃 관계는 드러납니다** — 같은 모양의 핸들러가 셋이고 베이스만
다릅니다:

| 명령 | 핸들러 | 플래시 베이스 | 내용 |
|---|---|---|---|
| `0x04` | `0x74de` | `0x20000` | 미확인 |
| `0x05` | `0x677c` | `0x20100` | 전역 설정 (§4.8) |
| `0xaa` | `0x711c` | `0x20300` | 보정 표 (§3.3) |

셋 다 쓰는 경로가 없습니다. `0x04` 는 확인만 하고 보내지는 않았습니다.

### 3.4 ⚠ 빈 페이로드도 쓰기다 [hw]

빈 페이로드 스윕 후 **LED 가 WASD 흰색으로 바뀌었습니다.** 처음에는 유독 느렸던
`0xa5`(24ms) / `0xa7`(21ms) / `0xdd`(54ms) 를 범인으로 봤지만 **틀렸습니다** —
그 셋을 제외한 두 번째 스윕에서도 똑같이 LED 가 바뀌었습니다.

§2.1 을 알고 나면 설명이 됩니다. 이 명령들은 **블록 쓰기**이고, 빈 페이로드는
"오프셋 0 에 0을 쓴다" 는 뜻입니다. 조명 블롭의 앞부분이 덮어써진 것으로 보입니다.
길이 필드가 0이어도 펌웨어가 그대로 쓰는 듯합니다.

따라서 안전한 명령은 부작용이 관찰되지 않은 세 개뿐입니다:

| 분류 | 명령 |
|------|------|
| 안전 (`SAFE_COMMANDS`) | `0x01`, `0x02`, `0x03`, `0xa9`, `0xaa` |
| 블록 쓰기 — 빈 페이로드로 보내지 말 것 | 나머지 전부 |

프로버가 기본적으로 안전한 명령만 보냅니다. 복구는 순정 드라이버에서 조명 프로파일을
다시 적용하면 됩니다.

### 3.5 트랜잭션

순정 드라이버는 **모든** 명령을 `0x01` … `0x02` 사이에서 보냅니다. 위 표는 각 명령을
단독으로 보낸 결과이므로, 대부분이 맨 ACK 만 돌려준 것이 이 때문일 수 있습니다.
프로버와 콘솔 모두 "0x01 … 0x02 로 감싸기" 옵션을 제공합니다.

### 3.6 `0x03` — 펌웨어 빌드 식별자 [fw] — 확정, 하드웨어 미검증

**보드에 "펌웨어 버전" 이라는 것은 없습니다.** 있는 것은 빌드 이름과 컴파일러가 박아
넣은 날짜·시각뿐이고, `0x03` 이 그 셋을 쉼표로 이어 돌려줍니다.

`0xaa` 와 마찬가지로 순정 드라이버는 이 명령을 보내지 않습니다. 분배표(`0x157b0`)의
`0x03` 항목이 `0x667c` 로 가고, 핸들러는 플래시의 NUL 종료 문자열 셋을 `payload[8..]`
로 복사하면서 사이에 `0x2c`(`,`) 를 넣은 뒤, 마지막에 총 길이를 `payload[4]` 에
씁니다. 즉 **응답 형태는 다른 블록 읽기와 같습니다** — 길이는 `payload[4]`, 데이터는
`payload[8]` 부터.

| 플래시 | 내용 | 실측값 |
|---|---|---|
| `0x15658` | 빌드 이름 | `HALL_HS_USB_KB` |
| `0x15668` | 컴파일러 `__DATE__` | `Nov 13 2024` |
| `0x15674` | 컴파일러 `__TIME__` | `11:05:59` |

```
HALL_HS_USB_KB,Nov 13 2024,11:05:59      (35바이트)
```

요청은 매직·명령·체크섬뿐이면 됩니다. 핸들러가 요청의 길이·오프셋 필드를 **읽지
않고** 길이를 자기가 채워 넣기 때문입니다.

핸들러 안에 플래시 쓰기가 없고 응답 버퍼(`gp+0x134`)에만 저장하므로 `0x03` 은
`SAFE_COMMANDS` 에 있습니다 — `0xaa` 와 같은 근거입니다 (§3.3).

> 값의 한계도 그대로 적어 둘 만합니다. 같은 날 빌드된 두 펌웨어는 구분되지 않고,
> 릴리스 번호와도 이어지지 않습니다. 그래도 펌웨어를 올리면 바뀌는 유일한 식별자라
> 설정 탭에서 "버전" 이 아니라 **빌드**로 표시합니다 (`src/ui/FirmwareInfo.tsx`).

### 3.7 ⚠⚠ `0xee` — 공장 초기화가 실제로 지우는 것 [fw] [bin] — 확정, 하드웨어 미검증

명령 자체는 §3 에서부터 알고 있었지만 **무엇이 지워지고 무엇이 남는지**는 펌웨어를
읽고서야 나왔습니다. 앱에 버튼을 붙이려면 그게 먼저 필요했습니다 — "전부 지워집니다"
라고만 적는 것은 사실 확인이 아니라 회피입니다.

#### 핸들러는 아무것도 지우지 않는다

`0xee` 핸들러(`0x76c6`)가 하는 일은 **플래그 한 바이트를 세우는 것뿐**입니다:

```
0076c6  c.li   a4, 1
0076c8  sb     a4, -0x791(gp)
0076cc  c.j    -> 0076d4          (공통 응답 경로)
```

그리고 바로 응답 경로로 떨어지므로 **ACK 는 즉시 돌아옵니다.** 즉 ACK 는 "요청을
받았다" 이상을 뜻하지 않습니다. 실제 작업은 메인 루프의 `0x1450c` 가 그 플래그를 보고
합니다.

#### 메인 루프가 다시 쓰는 영역

| 플래시 | 크기 | 무엇 | 출처 |
|---|---|---|---|
| `0x20100` | 64 B | 전역 설정 (§4.8) | 기본값 표 `0x175b4` |
| `0x20700` | 1024 B | 키맵 | `0x17ff4` |
| `0x20b00` | 1024 B | 키별 성능 | `0x177f4` |
| `0x20f00` | 512 B | 미확인 | `0x175f4` |
| `0x21100` 이후 | 4 KB + | 조명 블롭 | **0 으로 채움** |

**`0x20300` 은 이 목록에 없습니다.** 보정 표(§3.3)가 사는 곳이고, 초기화 루틴은 거기에
쓰지 않습니다 — 즉 **공장 초기화는 키 캘리브레이션을 지우지 않습니다.** 설정은 다시
넣으면 되지만 보정은 다시 학습시켜야 하는 것이라, 이 구분이 사용자에게 가장 중요한
사실입니다. 마지막에 `0xe1a4` / `0xe01e` / `0xe202` 를 부르는데 LED 재초기화로 보입니다.

#### 전역 설정의 공장 기본값 [fw]

기본값 표 `0x175b4` 의 앞 32바이트가 그대로 `0x05` 가 돌려주는 `payload[8..39]` 입니다:

```
50 00 aa bb 04 01 00 03 06 64 00 00 01 00 ff 00 …
```

앞 4바이트 `50 00 aa bb` 가 실측 헤더와 정확히 같습니다 — §4.8 의 오프셋 표가
독립적으로 한 번 더 확인된 셈입니다. 이어서:

| 필드 | 값 | 뜻 |
|---|---|---|
| `reporte_rate` | 4 | **1000 Hz** (§4.8 의 값 표 기준) |
| `tick_rate` | 0 | No tick rate |
| `dead_zone` | 1 | |
| `payload[15]` | `0x03` | Tachyon **켜짐**, 바닥 트리거 **켜짐**, `debounce_level` 0 (High) |
| 절전 | 6 분 | |

두 가지가 눈에 띕니다. 첫째, `reporte_rate = 4` 가 1000 Hz 라는 것 — 공장 기본값으로
가장 그럴듯한 값이고, §4.8 의 "1 = 8000 … 4 = 1000" 짝짓기를 **드라이버와 무관한
경로에서 지지**합니다. 둘째, 이 플래그 기본값은 순정 DB 의 기본값(§4.4, tachyon 0 ·
바닥 트리거 0)과 **다릅니다.** 초기화에서 이기는 쪽은 펌웨어입니다.

#### 이 앱의 절차

`src/protocol/raven61.ts` 의 `factoryReset()` 이 순정 그대로입니다 — `0x01`/`0x02` 로
감싸지 **않고** 단독 전송, `Sleep(1000)` + `Sleep(5000)`, 그 뒤 `0x05` 되읽기. 되읽은
값을 위 기본값 표와 대조해 어긋난 필드를 이름으로 보고하고, **답이 없으면 실패가 아니라
"읽지 못함" 으로** 보고합니다 — 아직 플래시를 쓰고 있을 수 있기 때문입니다.
UI(`src/ui/FactoryReset.tsx`)는 확인을 두 단계로 나눠 두었습니다.

### 4.1 스케일: 1 카운트 = 0.02 mm [db] — 확정

Esc 액추에이션만 바꿔 저장한 두 DB를 비교한 결과입니다.

| 순정 드라이버 설정 | `key_actuation` |
|---|---|
| 1.0 mm | 50 |
| 2.0 mm | 100 |
| 1.5 mm (공장 기본값 `global_key_actuation`) | 75 |

원점을 지나는 직선 위의 세 점 → **카운트 = mm x 50**, 즉 최소 단위 **0.02 mm**.
`rt_press` / `rt_release` / 데드존도 같은 스케일입니다 (기본 5 = 0.10 mm, 하단 데드존
기본 10 = 0.20 mm). `src/protocol/encoding.ts` 에 반영되어 있습니다.

### 4.2 `key_code` 는 HID usage 다 [db] — 확정

DB의 `key_code` 는 §6 의 `key_index` 가 **아닙니다**. 레이아웃 XML의 `code` 속성, 즉
HID usage 입니다. Esc = 41 (`0x29`), `1` = 30 (`0x1e`), LCtrl = 224 (`0xe0`),
Fn = 255 (`0xff`). `t_key_macro_data`, `t_userlightrgb_data` 도 동일합니다.

다만 이건 **드라이버 내부 모델**입니다. 실제 HID 명령이 usage 를 쓰는지 `key_index` 를
쓰는지는 아직 확인되지 않았습니다 — 캡처에서 Esc(41 vs 16) / A(4 vs 49) 를 비교하면
한 번에 갈립니다.

### 4.5 와이어 레코드 — `0xa0` 읽기 / `0xa1` 쓰기 [bin] [hw] — 확정

쓰기 절차는 §4.5.5.

키별 성능 설정은 **1024바이트 블록, 키 하나당 8바이트**입니다. 디코더 `0x427120` 와
인코더 `0x42c390` 이 정확히 서로의 역함수라는 것으로 확정했습니다.

```
rec[0]  bit 0-4  switch_type          읽을 때 & 0x1f
        bit 5-7  기기 플래그           이 보드는 0xa0 이 켜져 있음 (§4.5.2)
rec[1]           key_mode             0 = RT 끔, 1 = RT, 2 = RT + 전체 스트로크 퀵 트리거
rec[2..3] bit0-8 key_actuation − 1    9비트, 리틀엔디언
rec[4]
rec[5]  bit 0    rt_press − 1         9비트 (rec[5] bit0 이 최상위 비트)
rec[5]  bit 1-5  press_deadzone
rec[6]
rec[7]  bit 0    rt_release − 1       9비트
rec[7]  bit 1-5  release_deadzone
```

- 단위는 §4.1 과 같은 **1 카운트 = 0.02 mm**.
- 저장은 **−1 오프셋**입니다. 1.5 mm = 75 카운트 → 와이어에 74. 읽을 때 `+1`.
  근거: 인코더 `lea eax, [ecx-1]` (`0x42c53d`), 디코더 `inc ecx` (`0x427415`).
- 데드존은 5비트이므로 최대 31 = **0.62 mm**. RT 민감도와 동작 지점은 9비트이므로
  최대 512 = **10.24 mm**. 넘기면 실패가 아니라 **접혀 들어갑니다** — 1.00 mm 데드존은
  50카운트이고 `50 & 0x1f` 은 18, 즉 0.36 mm 가 조용히 들어갑니다. 그래서 인코더는
  마스크가 아니라 **포화(clamp)** 시키고, UI 입력 상한도 같은 숫자를 씁니다
  (`KEY_PERF_LIMITS`).
- RT 민감도 **최소는 1카운트**입니다. 인코더(`0x42c576`)와 순정 UI 의 스핀 핸들러
  (공용 컨트롤 `0x43ccd3`, 누름 컨트롤 `0x43d093`) 가 각각 독립적으로 1로 올려붙입니다.
- `deadzone_state` 는 와이어에 없습니다. 디코더가 **두 데드존 중 하나라도 0이 아니면 1**
  로 파생합니다 (`0x427437`, `0x427469`).
- 인코더는 쓰기 전에 `rt_press` / `rt_release` 를 **최소 1로 클램프**하고, 데드존 비트는
  `deadzone_state > 0 && 해당 데드존 > 0` 일 때만 싣습니다.

디코더가 채우는 구조체는 44바이트(11 dword)이고 `t_key_perf_data` 컬럼 순서와 1:1입니다
(§4.3). 배열은 `this+0x52bfc` 에 128 × 44바이트로 잡혀 있습니다 (`0x41ce93`).

공장 기본값이 바이너리에 상수로 박혀 있어 필드 순서를 독립 검증해 줍니다 —
"트리거 설정 초기화"(문자열 1403) 경로 `0x43a200` 이 쓰는 두 16바이트 상수:

```
0x582100:  03 00 00 00  01 00 00 00  4b 00 00 00  05 00 00 00
           switch_type=3 key_mode=1   actuation=75  rt_press=5
0x5820e0:  05 00 00 00  00 00 00 00  00 00 00 00  00 00 00 00
           rt_release=5  deadzone_state=0  press_dz=0  release_dz=0
```

성능 프리셋도 같은 7개 값을 넘깁니다 (`0x43dad2` 부근): `0xc9` = (1, 75, 5, 5, 0, 0, 0),
`0xca` = (1, 50, 5, 5, 0, 0, 0).

#### 4.5.1 `key_mode` 는 3값이다, 그리고 "분리"는 와이어에 없다 [bin] — 확정

`0` 끔 / `1` 래피드 트리거 / `2` 래피드 트리거 + **전체 스트로크 퀵 트리거**.

설정 키 `perf_continuerapidtrigger_mode` 는 어떤 패킷 빌더에도 나오지 않아 처음에는
"보드로 안 나간다" 고 봤는데 틀렸습니다. 토글 핸들러(`0x43d79e`)가 설정을 저장한 뒤
`0x43a990` 을 호출하고, 거기서 두 토글이 하나의 값으로 합쳐집니다 (`0x43aa13`–`0x43aa53`):

```
key_mode = 0
if (래피드 트리거 토글 [this+0x624])           key_mode = 1
if (전체 스트로크 퀵 트리거 토글 [this+0x680])  key_mode = 2
```

문자열 523 이 동작을 설명합니다: 켜면 "지정된 mm만큼 누른 후 완전히 떼지 않는 이상 항상
퀵 트리거", 끄면 "지정된 mm에서 바닥 영역까지만".

그러므로 **"연속 모드"는 독립된 비트가 아니고, 래피드 트리거를 끈 상태로 켤 수 없습니다.**
`key_mode 0` 이 끔이고 `2` 는 이미 켜짐을 포함합니다.

**"누름/뗌 분리"는 와이어에 아예 없습니다.** 보드는 항상 두 개의 민감도를 저장합니다.
순정 드라이버에도 같은 체크박스가 있고, 꺼져 있으면 컨트롤 하나의 값을 두 필드에 모두
넣습니다 (`0x43a9d7`–`0x43a9f6`: `[this+0x62c]` 가 분리 체크박스이고, 꺼져 있으면
`[[this+0x644]+0x144]` 하나를 press·release 양쪽에 씁니다). 이 프로젝트는 읽을 때
**반대 방향**으로 유도합니다 — 두 값이 다르면 체크박스가 켜집니다. 그래야 값이 서로
다르게 설정된 보드를 화면이 하나로 뭉개지 않습니다.

#### 4.5.2 `rec[0]` 상위 3비트 [bin] [hw] — 관측

인코더는 `[this+0x798]` 이 0이 아니면 `rec[0]` 에 `0xa0` 을 OR 합니다
(`0x42c51e`–`0x42c52a`). 이 플래그는 장치 열거 중에 정해집니다 (`0x42f450`–`0x42f479`):
`[dev+0x418] >= 0x108` 이면 1, 아니면 `word [dev+6]` 을 두 값과 비교해 같으면 0.

디코더는 `& 0x1f` 로 상위 3비트를 **버립니다.** 이 보드는 실제로 `0xa6` = `6 | 0xa0` 을
보고합니다 — 플래그가 켜져 있습니다. 의미는 미확정이므로 **읽은 값을 보존해서 되돌려주는
것**이 안전합니다 (`keyPerf.ts` 의 `switchFlags`).

#### 4.5.3 `ff ff ff ff` = 미설정 [hw] — 확정

RT 가 꺼진 키는 `rec[4..7]` 이 전부 `0xff` 입니다 (`a6 00 22 00 ff ff ff ff`). 그대로
해독하면 RT 민감도 512카운트, 데드존 31카운트(0.62 mm)가 나오는데 순정 화면은 그 키에
데드존을 표시하지 않습니다. **미설정 표식**입니다. `keyPerf.ts` 의 `rtUnset` 이 이를
처리하고, 쓸 때 다시 `0xff` 로 되돌립니다.

#### 4.5.4 블록 꼬리의 정체불명 레코드 [hw] — 미확정

슬롯 126·127 에 키가 아닌 레코드가 있습니다: `a1 00 95 00 09 3c 09 3c` →
switch 1, mode 0, 액추에이션 150(3.00 mm), RT 10/10(0.20 mm), 데드존 30/30(0.60 mm).
한계값 또는 템플릿으로 추정합니다.

#### 4.5.5 쓰기 절차 — 작업 `0x0d` / `0x42c390` [bin] — 확정 (하드웨어 미검증)

순정 드라이버의 "적용"은 읽기 절차를 그대로 뒤집은 것입니다. 명령별로 뜯으면:

| 순서 | 패킷 | 근거 |
|---|---|---|
| 1 | `0x01` | `mov word [ebp-0x53], 0x155` → `0x45a940` (`0x42c680`) |
| 2 | `0xa1` × 19 | 루프 `ebx = 0..0x12` (`0x42c6f7`–`0x42c7ce`) |
| 3 | `0x02` | `mov word [ebp-0x53], 0x255` → `0x45a940` (`0x42c7e9`) |

청크 하나의 필드는 읽기와 같은 자리입니다.

```
payload[4]      길이   0x38 = 56, 마지막(ebx == 0x12)만 0x10 = 16
                       cl=0x38 / cmove eax, 0x10  (0x42c712, 0x42c73f)
payload[5..6]   오프셋 ebx * 56, 리틀엔디언
                       ((ebx*8 - ebx) << 3) 로 계산  (0x42c70f–0x42c735)
payload[8..63]  데이터 SSE 4회로 16+16+16+8 = 56바이트 복사
                       (0x42c704, 0x42c738, 0x42c74e, 0x42c75b)
```

19 × 56 − 40 = 1024. 청크 사이에 `Sleep` 은 없습니다 — 헬퍼가 `WriteFile` 앞뒤로
각각 2 ms 씩 자고 있습니다 (§1.1).

**순정 드라이버는 스테이징 버퍼를 0으로 밀고 시작합니다** (`memset(buf, 0, 0x400)` at
`0x42c44b`). 그 다음 자기 키 컬렉션에 있는 슬롯만 채우므로, 자기가 모르는 슬롯 —
126·127 과 쓰이지 않는 채널 3개 — 은 **0으로 나갑니다**.

#### 4.5.6 이 프로젝트의 쓰기는 읽기-수정-쓰기다

같은 방식으로 블록을 만들지 않습니다. 슬롯 128칸 중 키는 61개뿐이고, 126·127 에는
키가 아닌 레코드가 있으며(§4.5.4) `rec[0]` 상위 3비트의 의미는 아직 모릅니다(§4.5.2).
모델에서 블록을 만들면 그 전부가 0이 되어 나갑니다.

그래서 `writeKeyPerfConfigs()` 는:

1. 키맵(`0x07`)과 성능 블록(`0xa0`)을 **먼저 읽습니다**
2. 사용자가 바꾼 키의 슬롯에 8바이트만 갈아끼웁니다 (`patchSlot`)
3. 19청크 전부를 씁니다 — 건드리지 않은 바이트는 방금 읽은 값 그대로
4. **다시 읽어 바이트를 대조합니다**

`switch_type` 과 `rec[0]` 상위 비트, `ff ff ff ff` 표식은 이 앱이 설정하지 않는
값이므로 **보드가 준 레코드에서 그대로 가져옵니다** (`fromKeyConfig(config, current)`).
읽기 전에 쓰면 공장 기본값 `KeyConfig` 에는 `switch_type` 이 없어서 스위치 종류가
0번으로 선언되고 상위 비트가 지워집니다 — UI 도 읽기 전에는 쓰기 버튼을 잠급니다.

**슬롯 매핑이 키맵에서 오지 않으면 쓰지 않습니다.** 키맵 읽기가 실패하면 읽기 경로는
레이아웃 순서 추정값으로 내려가도 쓸모가 있습니다 — 값이 엉뚱한 키에 붙어 보이지만
보드는 그대로입니다. 쓰기는 다릅니다. 그 추정 배치는 **실제 보드와 다르다는 것이
확인된** 배치이므로(§4.6, 행별 액추에이션 실험), 그대로 쓰면 다른 키의 설정이 바뀝니다.

4번이 형식적인 절차가 아닌 이유: **ACK 하고 무시하는 쓰기는 성공한 쓰기와 구별되지
않습니다.** 프레임은 요청 에코이므로(§3.1) 응답만 봐서는 반영 여부를 알 수 없고,
읽기 경로는 별개의 코드라 UI 표시가 맞아 보이는 것도 근거가 되지 못합니다.

패킷 순서와 위 성질은 `tools/check/perf-write.ts` 가 가짜 보드로 검사합니다
(`npm run check`) — 청크 개수·오프셋·길이, `0x01`/`0x02` 위치, 무시하는 보드와
한 바이트를 고치는 보드가 실패로 보고되는지, 슬롯을 못 찾은 키가 조용히 넘어가지
않는지, 그리고 `switch_type` 이 보존되는지.

> **아직 확인 전:** `0x02` 가 RAM 적용인지 플래시 저장인지 (§9). 순정 드라이버의
> 적용 버튼이 이 순서를 그대로 보내므로 저장까지 되는 것으로 보이지만 확인하지
> 않았습니다.

### 4.6 슬롯 매핑 — 보드에서 받아야 한다 [bin] [hw] — 확정

성능(`0xa0`) · 키맵(`0x07`) · RGB(`0xde`) 블록은 **같은 슬롯 번호 공간**을 씁니다.
그리고 그 번호는 **레이아웃 파일에서 계산할 수 없습니다.**

하드웨어 덤프에서 채워진 성능 슬롯이 **정확히 61개**, 0–63 안에 있고 **12·20·53 이
빕니다.** 슬롯 공간은 64칸이고 3칸이 안 쓰입니다 (61 + 3 = 64).

행마다 다른 동작 지점(0.10 / 0.70 / 1.30 / 1.80 / 2.60 mm = 5 / 35 / 65 / 90 / 130
카운트)을 넣고 읽어서 슬롯의 행을 역산했습니다:

| 행 | 키 수 | 슬롯 |
|---|---|---|
| 0 (Esc–Backspace) | 14 | 3, 24–27, 33, 36, 40–44, 58, 59 |
| 1 (Tab–백슬래시) | 14 | 0–2, 11, 17, 19, 28, 34, 35, 51, 52, 56, 57, 60 |
| 2 (Caps–Enter) | 13 | 4, 8–10, 18, 22, 38, 39, 48–50, 55, 63 |
| 3 (Shift–Shift) | 12 | 5, 6, 13, 14, 16, 21, 23, 29, 32, 46, 47, 54 |
| 4 (Ctrl–Fn) | 8 | 7, 15, 30, 31, 37, 45, 61, 62 |

키 수가 14/14/13/12/8 로 실제 행과 정확히 일치하고, **어떤 규칙으로도 계산되지
않습니다** — `slot mod 8`, `slot div 8`, `row_col`(row×16+col), 레이아웃 순서 모두 이
배치를 만들지 못합니다. 하드웨어 배선입니다. 바이너리에 정적 테이블도 없습니다 (위 행
제약으로 바이트·워드 폭 전수 검색 → 61칸 중 30칸 이상 맞는 창이 0개).

순정 드라이버도 계산하지 않습니다. `슬롯 → usage` 맵(`this+0xbc4`)과 역방향 맵 두 개를
**키맵 블록에서** 만듭니다 (`0x426344`–`0x4264c1`, `this+0x8a4` 에 캐시된 `0x07` 블록):

```
base = this+0x8a4 + 슬롯*3
entry[0] = 0x10  → 일반 키          (0x20/0x21 미디어, 0x30, 0x70 등은 무시)
entry[1] = HID 수정자 비트마스크      1 LCtrl, 2 LShift, 4 LAlt, 8 LGui,
                                    0x10 RCtrl, 0x20 RShift, 0x40 RAlt, 0x80 RGui
                                    0 이 아니면 이쪽이 우선 — 수정자는 entry[2] 가 0
entry[2] = HID usage
entry[0] = 0xf0 && entry[1] = 0xff → Fn (usage 0xff)
```

`0x426395` 의 128칸 점프 테이블이 비트마스크를 `0xe0`–`0xe7` 로 바꾸고, `0x45d990` 이
그 역변환(`0xe0..0xe7` → `1, 2, 4, 8, 0x10, 0x20, 0x40, 0x80`)이라 서로 확인됩니다.
아날로그 이벤트가 `payload[2]` 로 수정자를 식별하는 것과 같은 방식입니다 (§3.2).

`src/protocol/slotMap.ts` 가 이 형식 그대로 해독합니다. 읽기가 실패하거나 57키 미만만
해석되면 추정 매핑으로 내려가고 **UI 가 "추정값" 이라고 표시**합니다 — 추정 매핑은 위
실측과 다르므로 조용히 쓰이면 안 됩니다.

> ⚠ `0x0a`(384 B)를 키맵으로 읽으면 **전부 0** 입니다. 미할당 FN 레이어로 보입니다.
> 맵의 출처는 **`0x07`** 입니다.

### 4.7 `switch_type` 열거값 [hw] [bin] — 확정

**이름은 하드웨어 측정값입니다.** 순정 드라이버에서 스위치 종류를 전체 키에 하나씩
적용하고 읽어서 값↔이름을 확인했습니다.

| `switch_type` | 이름 | 총 스트로크 | 비고 |
|---|---|---|---|
| 0 | Magnetic Orange | 4.00 mm | 바이너리 추정은 Light Breeze — **틀렸음** |
| 1 | Magnetic White | 4.00 mm | 추정은 Light Breeze V2 — **틀렸음** |
| 2 | Magnetic Jade | 3.32 mm | 일치 |
| 3 | Light Breeze | 4.00 mm | 추정은 Magnetic White — **틀렸음** |
| 4 | Light Breeze V2 | 3.80 mm | 추정은 Magnetic Orange — **틀렸음** |
| 5 | GEON RAW HE | 3.50 mm | 일치 |
| 6 | TTC Magneto | 3.40 mm | 일치 |
| 7 | Chocolate Dwarf | 2.50 mm | 일치. **실물이 없는 스위치** — 아래 참고 |

> `switch_type 7` **Chocolate Dwarf 는 실제로 존재하지 않는 스위치입니다** (보드 소유자
> 확인). 드라이버 표에 있으므로 디코딩은 그대로 하되, 웹 드라이버의 선택 목록에서는
> 제외했습니다 (`SELECTABLE_SWITCH_TYPES`) — 없는 스위치를 쓰면 보드는 그 키의 스트로크를
> 2.50 mm 로 알게 되고, 그 기준으로 재는 모든 깊이가 어긋납니다. 보드가 이미 그 값을
> 갖고 있으면 **읽은 그대로 다시 씁니다**; 새로 쓰지만 않습니다.

**총 스트로크는 이름이 아니라 값에 붙어 있습니다.** 순정은 `0x576c8c` 의 dword 표를
원본 `switch_type` 값으로 색인하고(`0x43a7df`) 같은 값을 `SetCurSel` 에도 넘깁니다.
그래서 이름 순서가 바뀌어도 표는 그대로입니다. 3.32 / 3.80 / 3.50 / 3.40 / 2.50 mm 항목이
있으니 **총 스트로크를 4 mm 로 가정하면 안 됩니다.**

> 정정: 이름 순서를 언어 문자열 1450–1457 의 가변인자 push 순서(`0x44af0d`–`0x44aff8`)로
> 추정했는데, 하드웨어에서 8개 중 4개(0↔4, 1↔3 형태)가 어긋났습니다. **그 push 순서가
> 콤보박스의 최종 순서가 아닙니다.** 어디서 재배열되는지는 미해결 (§9).

기기 종류에 따라 이 표를 안 쓰는 경로도 있습니다 (`0x43a7c4`): 장치 타입 `0x65` / `0x66`
은 표를 쓰고, `0x67` 은 `(0, 400)` 으로 고정합니다. `config.xml` 의 `device_type="101"`
= `0x65` 이므로 이 보드는 표를 씁니다.

문자열 502–504 (`Jiadalong Magnetic Jade Axis` / `... White Axis` / `Hejin axis`) 는
다른 모델의 3종 목록이며 이 표와 무관합니다.

### 4.8 전역 설정 블록 — `0x05` 읽기 / `0x06` 쓰기 [bin] [hw] — 확정

§4.4 는 순정 드라이버 **DB** 의 전역 설정이고, 이쪽은 **와이어** 블록입니다. 32바이트,
요청에 `payload[4] = 0x20`, 오프셋 0, 데이터는 `payload[8..39]`.

호출부는 두 곳입니다 — `0x429560`(성능 탭 진입)이 `payload[12..15]` 를, `0x428a30`
(일반 설정)이 `payload[16..24]` 를 수정합니다. **둘 다 블록을 먼저 읽어 응답을 그대로
쓰기 버퍼에 복사한 다음** 자기 범위만 고칩니다 — 절차는 §4.8.1. `0x429300` 이 같은
바이트를 읽어 UI 에 올리는 것까지 확인해 왕복 검증됐습니다.

| payload | 비트 | 내용 |
|---|---|---|
| `[8..11]` | | 헤더. 실측 `50 00 aa bb` — `aa bb` 는 마커로 보입니다 |
| `[12]` | 0-3 | `reporte_rate` — `0x429300` 이 `& 0x0f` 로 되읽음 |
| | 4-7 | `tick_rate` |
| `[13]` | | `dead_zone` |
| `[14]` | 0 / 1 / 2 | `disable_win` / `disable_alttab` / `disable_altf4` |
| `[15]` | 0 | `perf_tachyon_mode` |
| | 1 | `perf_bottomrapidtrigger_mode` — **"바닥까지 입력시 트리거"** |
| | 2 | `actuation_check` |
| | 3 | 자석축 테스트 / 성능 탭 활성 |
| | 5-6 | `debounce_level` — `0x429300` 이 `>> 5` 로 되읽음 |
| `[16]` | | 슬립 시간(분). `0x17` 이상이면 `0xff` |
| `[17..21]` | | 조명 · 일반 설정 (밝기 계열은 `4 − x` 로 반전) |
| `[22..24]` | | 24비트 RGB |

**성능 탭의 6개 항목 중 이것만 전역**입니다. 나머지(동작 지점 · RT 활성 · RT 민감도 ·
전체 스트로크 퀵 트리거 · 스위치 종류)는 전부 키별 레코드에 있습니다 (§4.5).

##### 값의 의미 — 폴링 레이트 · 틱 레이트 · 디바운스 [bin] [lang] — 하드웨어 미검증

바이트 위치는 위 표로 확정됐지만 **값이 무엇을 뜻하는지는** 순정 UI 가 자기 콤보
박스를 채우는 코드에서 나왔습니다. 항목마다 `AddString` 호출 직전에 언어 문자열 id 와
**그 항목의 값**을 같이 밀어 넣습니다:

| 필드 | 코드 | 값 → 문자열 |
|---|---|---|
| `tick_rate` | `0x44410d`–`0x4441eb` | 0 → 70 "No Tick rate", 1 → 71 "30", 2 → 72 "60" |
| `debounce_level` | `0x44427e`–`0x444362` | 0 → 75 "High", 1 → 76 "Medium", 2 → 77 "Low" |
| `reporte_rate` | `0x4443ef`–`0x444527` | **1 → 80 "8000Hz", 2 → 81 "4000Hz", 3 → 82 "2000Hz", 4 → 83 "1000Hz"** |

폴링 레이트만 0 이 아니라 1 부터 시작한다는 점에 주의하세요. 값이 목록의 인덱스가
아니라는 뜻이고, 실제로 순정 DB 도 그 범위 안에서만 값을 갖습니다 — 기본 프로파일이
`reporte_rate = 1`, 사용자 프로파일 셋이 전부 `4` 입니다. 8000 Hz 가 목록에 있는 것도
이상하지 않습니다: 펌웨어가 스스로를 `HALL_HS_USB_KB` 라고 부르고, 8000 Hz 는 USB
고속(HS)이라야 나옵니다.

**`debounce_level` 이 몇 ms 인지는 어디에도 없습니다.** 순정 드라이버에도 펌웨어에도
없어서, 이 앱은 High / Medium / Low 라는 이름과 원본 값만 보여주고 ms 로 환산하지
않습니다.

미검증인 부분도 분명히 해 두면 — 순정에서 폴링 레이트를 바꾸는 캡처를 뜬 적이 없으므로
위 짝짓기는 **드라이버 코드에만** 근거합니다. 그리고 레이트를 바꾸면 보드가 USB 를 다시
잡을 수 있어, 쓰기 뒤 되읽기가 실패하는 것이 정상 동작일 수 있습니다
(`src/ui/BoardSettings.tsx` 가 그 경우를 따로 안내합니다).

#### 4.8.1 전역 설정 쓰기 — `0x06` 은 순정도 읽기-수정-쓰기다 [bin] — 확정

`0x06` 호출부는 두 곳이고, **둘 다 같은 다섯 단계**입니다.

| 단계 | 성능 탭 (`0x429560`, 작업 `0x0e`) | 일반 설정 (`0x428a30`, 작업 9) |
|---|---|---|
| 1 | `0x01` (`0x4295ba`) | `0x01` (`0x428ab4`) |
| 2 | `0x05`, `payload[4] = 0x20`, **읽기 헬퍼** (`0x4295e0`, `0x4295f5`) | 같음 (`0x428ae3`, `0x428b01`) |
| 3 | **응답 65바이트를 쓰기 버퍼로 복사** — SSE 4회 (`0x42960a`–`0x42964d`) | 같음 (`0x428b13`–`0x428b93`) |
| 4 | `payload[0..1]` 을 `55 06` 으로 덮고 자기 필드만 수정 → 전송 | 같음 |
| 5 | `Sleep(400)` (`0x4299e9`) 뒤 `0x02` | `0x02` |

성능 탭 경로가 수정하는 바이트:

```
payload[12]  reporte_rate | tick_rate << 4     (0x4296e6)
payload[13]  dead_zone                          (0x429721)
payload[14]  disable_win | alt_tab<<1 | alt_f4<<2 (0x429887)
payload[15]  플래그 — §4.8                       (0x4299d7)
```

> **정정.** 이전 판에는 "두 호출부가 서로 겹치지 않는 범위를 쓰고 나머지는 0으로
> 남기므로, 펌웨어가 필드를 독립적으로 취급하는 것으로 보인다" 고 적혀 있었습니다.
> **틀렸습니다.** 두 호출부 모두 3단계에서 `0x05` 응답을 그대로 복사하므로,
> **어느 쪽도 대부분이 0인 블록을 보내지 않습니다.** 필드 독립성에 대한 근거는
> 처음부터 없었습니다.
>
> 이 앱의 `enableAnalogReport()` 가 그 서술 위에 만들어져 있었고, 따라서
> `payload[15]` 만 세운 채 폴링 레이트 · 데드존 · 게임 잠금 · 절전 시간을 **매번
> 0으로 덮어쓰고** 있었습니다. `writeGlobalSettings()` 로 교체했습니다.

이 프로젝트도 같은 절차입니다 — `writeGlobalSettings()` 가 블록을 읽어 이름 붙은
비트만 바꾸고(`patchGlobalFlags`), 보낸 뒤 다시 읽어 `payload[15]` 를 대조합니다.
바꿀 것이 없으면 아무것도 보내지 않고 그렇게 보고합니다.

### 4.9 읽는 시점 [bin] — 성능 탭 진입이 아니다

탭 전환 핸들러 `0x43933c` 는 탭 7 진입 시 작업 코드 `0x0e` 하나만 큐에 넣고, 그 핸들러
`0x429560` 은 전역 블록의 읽기-수정-쓰기만 합니다. **키별 값은 이때 읽지 않습니다.**

`0xa0` 읽기가 도는 경로는 세 곳이고 모두 같은 시퀀스를 씁니다:

```
0x4434e0  연결 완료 · 프로파일 전환 (작업 코드 4, 5)
0x443540  공장 초기화 직후 (작업 코드 0x0c)
0x42cabe  보드가 0xa2 리포트를 올려보냈을 때

  0x429300  장치 정보 (0x05)
  0x427120  키별 성능 (0xa0)   <-- 여기
  0x43a3b0  성능 탭 UI 채우기
  0x427590  키맵 (0x0a)
```

읽은 레코드는 유효한 것만 모아 SQLite `t_key_perf_data` 로 동기화됩니다 (`0x427533`).
그래서 순정에서 탭을 열면 값이 즉시 보입니다 — 이미 읽어서 DB 에 넣어 뒀기 때문입니다.

비요청 리포트는 첫 바이트로 갈립니다 (`0x42c8a0`, 쓰기 없이 10 ms 타임아웃 읽기만):

| `payload[0]` | 의미 |
|---|---|
| `0xa0` | 키 아날로그 이벤트 — **탭 7일 때만** 처리 (`0x42c912`) |
| `0xa1` | 프로파일 변경 알림. `payload[1]` 이 새 프로파일 |
| `0xa2` | **전체 재읽기 알림** — 위 시퀀스를 통째로 재실행 |

`0xa2` 는 보드가 스스로 "설정이 바뀌었으니 다시 읽어라" 고 알릴 수 있다는 뜻입니다.

```sql
  macro_type, key1_value, key2_value, key1_name, key2_name, reserved)
t_key_item_data(keyitem_id, macro_id,
  trigger_state1, trigger_state2, trigger_state3, trigger_state4,
  key_value, key_name)
```

`macro_type` 이 종류를 구분하며, UI 문자열상 다음 6종입니다 [bin]:

| 약어 | 이름 | 설명 |
|------|------|------|
| DKS | Dynamic Keystroke | 4단계 깊이에 최대 4개 기능. `trigger_state1..4` |
| MT | Mod Tap | 짧게 누르면 탭, 길게 누르면 수정자 (기본 200ms) |
| TGL | Toggle | 누르면 트리거 위치로 잠금 |
| RS | Rappy Snappy | 두 키 중 더 깊이 눌린 쪽 활성화 |
| SOCD | Snappy Tappy | 입력 우선순위 정리 |
| OKS | — | 키를 **뗄 때** 바인딩 키가 발동 |

프로파일당 고급 키는 최대 40개 [bin].

## 6. 키 주소 [xml] [bin] [hw] — 정정됨

> **정정.** 이전 판은 "`layouts/Raven61.xml` 의 `key_index` 가 펌웨어 키 주소입니다" 라고
> 적었습니다. **틀렸습니다.** 순정 드라이버는 `key_index` 를 **어디에도 쓰지 않습니다.**

레이아웃 XML 파서(`0x42dd10`)가 `key_index` 를 파싱하고 결과를 버립니다:

```
0042e9bd  mov  dword [eax], 0x57aaf0   ; "key_index"
0042e9d7  push eax
0042e9d8  call ebx                     ; atoi   (바이트: 50 ff d3)
0042e9da  mov  eax, [ebp-0x1a8]        ; <-- 반환값을 덮어씀. 저장 없음
```

`light_index` 도 같습니다 (`0x42ea1e`). 두 속성 이름 문자열은 **바이너리 전체에서 이
한 곳에서만** 참조됩니다. 같은 파서가 `code`(HID usage)는 `strtol(…, 16)` 으로 읽어
보관합니다 (`0x42e896`).

프로토콜에서 키를 지정하는 세 가지를 구분해야 합니다:

| 이름 | 어디에 쓰이나 | 값의 예 |
|---|---|---|
| **슬롯** | **와이어 블록 전부** (`0xa0` 성능, `0x07` 키맵, `0xde` RGB) | 0–63 중 61칸, §4.6 |
| HID usage | 순정 DB `t_key_perf_data.key_code`, 아날로그 이벤트 `payload[3]` | Esc 41, A 4 |
| `key_index` | **아무데도** — XML 에만 남아 있는 사문 | Esc 16, Backspace 92 |

슬롯은 계산할 수 없고 보드에서 받아야 합니다 (§4.6). `src/keyboard/raven61.ts` 는
`keyIndex` / `lightIndex` 필드를 여전히 XML 그대로 담고 있지만 **프로토콜에 쓰지
않습니다** — 순정 XML 의 기록으로만 남겨 둡니다.

### 6.1 XML 이 실제로 주는 것 [xml]

- `code` — 기본 HID usage. 슬롯 매핑이 이 값으로 키를 식별하므로 여전히 핵심입니다.
- `row_col` — UI 그리드 위치 (`row#col`, `col_count=16`). **와이어 주소가 아닙니다** —
  이 가설도 하드웨어에서 배제됐습니다 (§4.6).
- `rect_*` — 순정 UI 의 픽셀 좌표.
- `name` / `desc` — 라벨. `]` 키의 `name` 이 `[` 로 적힌 오기가 있습니다.

참고로 `key_index` 값 자체는 규칙적입니다 (숫자열 16–28, Q행 32–44, A행 48–59,
Z행 64–74, 하단 80–87). 16 단위 행 경계라 **행렬 주소처럼 보이지만**, 위에서 본 대로
쓰이지 않습니다. `light_index` 에는 `-` 키가 `T` 와 같은 37로 적힌 오기가 있습니다.

하단 행 순서는 **Ctrl, Win, Alt, Space, Alt, Menu, Ctrl, Fn** 입니다 — Fn이 맨 오른쪽.

## 7. 레이어와 프로파일 [db] — 확정

- **프로파일 3개** (`t_profile_data`: Profile 1/2/3). `t_config_data` 의 프로파일 0은
  공장 기본값 행입니다.
- **레이어 4개** (`t_key_macro_data.fn_layer` 0–3). 순정 드라이버 UI 문구에는 FN Layer
  1–8 이 있지만 이 보드 데이터에는 0–3만 존재하며, 2·3은 전부 미할당입니다.
  UI 문구는 여러 모델이 공유하는 텍스트로 보입니다.
- `fn_layer` **101** 이 프로파일 1에만 추가로 존재합니다. 0번과 1번을 합친 형태이고,
  Fn 키 자신이 `macro_type=12, macro_value=511 (desc "FN1")` 즉 **레이어 전환 액션**으로
  들어가 있습니다. 0/1번에서는 Fn 키가 HID usage 228(RCtrl)로 저장됩니다.
  역할 미확정 — 보드에 실제로 내려가는 통합 키맵일 가능성 (추측).
- `macro_type`: **2 = 일반 HID 키** (`macro_value` 가 usage), **12 = 특수 액션**
  (`macro_value` 1 = 미할당, 511 = FN1 레이어 전환) [db]

## 9. 미해결 질문

- [ ] **`0x06` 하드웨어 검증.** `payload[15]` bit 1(바닥까지 트리거)을 읽기-수정-쓰기로
      바꾸고 다시 읽어 대조하는 경로를 구현했습니다 (§4.8.1). 실제 장치에서는 아직
      확인 전입니다
- [ ] **`0xa1` 하드웨어 검증.** 인코더 · 청크 순서 · 읽기-수정-쓰기까지 구현했고
      가짜 보드 검사도 통과했지만(§4.5.5, `npm run check`) 실제 장치에 써 보지
      않았습니다. 앱이 쓴 뒤 다시 읽어 바이트를 대조하므로, 반영되지 않으면
      "기록한 값과 다르게 읽힌 슬롯" 으로 표시됩니다
- [ ] **폴링 레이트 값 하드웨어 검증.** `reporte_rate` 1–4 ↔ 8000–1000 Hz 짝짓기는
      순정 콤보 박스를 채우는 코드 하나에만 근거합니다 (§4.8). 순정에서 레이트를 바꾼 뒤
      `0x05` 로 되읽으면 확정됩니다. 레이트를 바꾸면 보드가 USB 를 다시 잡을 수 있어,
      쓰기 뒤 되읽기 실패가 정상일 수 있다는 점도 같이 확인해야 합니다
- [ ] **`debounce_level` 의 실제 시간.** High / Medium / Low 라는 이름 말고 ms 값이
      드라이버에도 펌웨어에도 없습니다 (§4.8). 펌웨어의 키 스캔 루프에서 이 값을 읽는
      곳을 찾으면 나올 것으로 보입니다
- [ ] `0x0d`(3584 B)와 `0x08`(512 B, 베이스 오프셋 인자)의 내용
- [ ] `0x04`(플래시 `0x20000` 블록 읽기)가 무엇을 담고 있는가 (§3.2 분배표)
- [ ] **`0xee` 하드웨어 검증.** 초기화가 무엇을 다시 쓰는지는 펌웨어에서 읽었지만
      (§3.7) 실제로 보내 본 적은 없습니다. 보드에서 확인할 것: 6초 뒤 `0x05` 가
      기본값 표와 같은 값을 돌려주는가, **보정 표(`0xaa`)가 정말 그대로인가**,
      그리고 초기화 중 USB 가 끊기는가
- [ ] 초기화가 `0x20f00` 에 512바이트를 되쓰는데 그 블록이 무엇인가 (§3.7)
- [ ] `0x0c` 가 `0x0d` 의 읽기 짝인가 (§3 의 읽기=쓰기−1 규칙)
- [ ] 슬롯 12 / 20 / 53 이 비는 이유 — 하드웨어 채널 배치로 추정 (§4.6)
- [ ] 성능 블록 슬롯 126 / 127 의 레코드가 무엇인가 (§4.5.4)
- [ ] `rec[0]` 상위 3비트(`0xa0`)의 의미 (§4.5.2). 펌웨어 버전 게이트로 보이지만 미확정
- [ ] 스위치 콤보박스가 언어 문자열 1450–1457 을 **어디서 재배열**하는가 (§4.7).
      이름 자체는 하드웨어로 확정됐으므로 기능상 막힌 것은 없습니다
- [ ] `0x02` 종료 패킷의 `payload[4] = 0x20`(전역 설정 경로)이 무엇인가
- [ ] 아날로그 이벤트의 `payload[8]` 이 무엇인가 (래피드 트리거 기준점 추정)
- [ ] **보정 판정의 문턱값.** ADC 진폭을 초록/노랑/빨강으로 가르는 경계가 `mui.dll` 의
      그리기 경로 안에 있어 찾지 못했습니다 (§3.2). 절대 하한 `minSwing` 과 중앙값 대비
      비율로 대신하고 있고, 나쁜 키가 있는 보드에서 순정 화면과 대조해 본 적이 없습니다.
      캘리브레이션 패널의 "측정값 복사" 가 그 대조를 위한 것입니다
- [ ] `payload[10]` = `check_count` 가 무엇을 세는가 (§3.2). 보정 상태 표시로 함께
      넘어가지만(`SetKeyCalibration` 3번째 인자) 쓰이는지는 미확인
- [ ] `payload[12..13]` 이 정확히 무엇인가 (주소가 아님 — 캘리브레이션 파라미터 추정)
- [ ] 표시 깊이 환산의 `총스트로크 − 5` 에서 5 의 근거 (§3.2)
- [ ] `0x02` 가 RAM 적용인가 플래시 저장인가
- [ ] 아날로그 테스트 모드의 캘리브레이션이 **무엇을 어디에 쓰는가** (§3.2).
      한 키만 바닥까지 누르고 나머지 기준 ADC 가 그대로인지 보면 범위가 갈립니다
- [ ] 지문 `0601:0` 이벤트의 정체 (§3.2). 키 이벤트가 아니지만 계속 올라옵니다
- [ ] `key_index` / `light_index` 는 무엇을 위해 XML 에 남아 있는가 (§6, 아무도 안 씀)
- [ ] `fn_layer` 101 의 역할
- [ ] `perf_sensitivity_mode` / `perf_tachyon_mode` 의 의미
