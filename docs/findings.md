# Raven61 추론 기록

[protocol.md](./protocol.md) 는 **무엇이 사실인가**를 적습니다.
[reverse-engineering.md](./reverse-engineering.md) 는 **어떻게 캡처하는가**를 적습니다.

이 문서는 **어떻게 알아냈는가** 를 적습니다 — 각 결론이 무슨 증거에 얹혀 있고, 얼마나
믿을 수 있고, 어떤 결론이 틀렸다가 무엇에 의해 잡혔는지. 사실 자체는 여기서 반복하지
않고 명세의 절을 가리킵니다.

## 0. 출발점

순정 드라이버는 **PE32/x86 MFC C++ 윈도우 네이티브 exe** 입니다. Electron 이 아니라서
자바스크립트를 읽는 손쉬운 길이 없었습니다.

그리고 **USB 캡처가 전부 실패했습니다.** 이게 이 프로젝트의 방법론을 결정했습니다.
캡처가 됐다면 와이어 포맷을 그냥 읽으면 끝이었을 일을, 캡처 없이 세 갈래로 우회해야
했습니다.

| 경로 | 무엇을 주는가 |
|------|---------------|
| **정적 분석** — 임포트 표, IAT 호출 지점, 디스어셈블 | 드라이버가 **보내려고 의도한** 형식 |
| **순정 데이터 파일** — SQLite DB, 레이아웃 XML | 설정 **값**의 의미와 스케일 |
| **보드에 직접 질문** — 웹 드라이버의 프로버·이벤트 탭 | 보드가 **실제로 하는** 행동 |

세 경로가 각각 답할 수 없는 것이 있고, 그 공백이 지금 미해결로 남은 것과 정확히
일치합니다 (§5).

## 1. 증거 등급

명세의 `[bin]` `[db]` `[xml]` `[hw]` `[cap]` 태그는 출처 표기이자 **증명력의 등급**입니다.

| 등급 | 증명하는 것 | 증명하지 못하는 것 |
|------|-------------|--------------------|
| `[bin]` 정적 분석 | 드라이버 코드가 무엇을 만드는가 | 그 코드가 실행되는가 (→ 오류 #1) |
| `[db]` 순정 DB | 드라이버 내부 데이터 모델 | 그 모델이 와이어에 그대로 나가는가 (→ §5) |
| `[xml]` 레이아웃 | 키 주소와 물리 위치의 대응 | 명령이 그 주소를 쓰는가 |
| `[hw]` 하드웨어 관측 | 보드가 실제로 무엇을 보내는가 | 보드가 무엇을 **받는지** — 응답이 에코라서 |
| `[cap]` USB 캡처 | 와이어 포맷 그 자체 | **확보 실패 — 이게 남은 공백의 원인** |

핵심은 이렇습니다. `[bin]` 은 **의도**를, `[hw]` 는 **결과**를 봅니다. 읽기 방향은
`[hw]` 로 완전히 검증됐고, **쓰기 방향은 어느 등급으로도 검증할 수 없습니다** — 명령
응답이 요청의 에코일 뿐이라 보드가 무엇을 이해했는지 알려주지 않기 때문입니다.

## 2. 추론 사슬

### 2.1 전송 계층 — "문자열이 있다" 가 아니라 "몇 번 호출되는가"

사슬: 문자열 → 임포트 표 → IAT 호출 지점 → 송수신 헬퍼 디스어셈블.

결정적이었던 것은 `HidD_SetFeature` **문자열의 존재가 아니라 참조 횟수**였습니다.
`GetProcAddress` 로 받은 주소가 전역 `0x5a1f98` 에 저장되는 참조가 **1건, 호출 0건**.
`CH375*` 임포트 8개도 전부 호출 0건인 죽은 코드였습니다.

그 다음에 `0x45a940` 이 **모든 명령이 공통으로 쓰는 단 하나의 송수신 헬퍼**라는 걸
찾은 게 표를 열었습니다. 호출 지점 52곳을 모으고 각 호출자에서 명령 바이트가
즉시값(immediate)으로 들어가는 걸 읽으면 명령 표가 나옵니다 — `tools/bin/commands.py`
가 하는 일입니다.

→ 명세 §1, §3

### 2.2 프레임 — 루프의 *모양*이 알고리즘을 준다

체크섬 루프 `0x45a9a5`–`0x45a9dc` 는 10회 × 6바이트로 펼쳐진(unrolled) 형태입니다.
루프 횟수와 스트라이드만 읽어도 **범위 60바이트**가 나오고, 누산 방식에서 **단순 8비트
합**이 나옵니다. 그리고 결과를 `[esi+4]` 에 저장하므로 **체크섬은 자기 다음 바이트부터
끝까지를 덮습니다** — 자기 자신은 포함하지 않습니다. 구현할 때 틀리기 쉬운 부분이라
코드에서 직접 읽어낸 값이 중요했습니다.

응답이 **요청의 에코**(`payload[0]` 만 `0xAA`)라는 건 하드웨어에서 확인했고, 이게 왜
중요한지는 §1 마지막 문단과 같습니다: **명령의 성공 여부를 알려주는 채널이 없다.**
초기 스윕에서 13개 명령이 전부 "ACK" 를 돌려준 건 전부 이해했다는 뜻이 아니라
**아무 의미도 없었다**는 뜻이었습니다.

→ 명세 §2, §3.1

### 2.3 재구성 — 13개 기능이 아니라 하나의 블록 전송

이게 이 프로젝트에서 가장 큰 관점 전환이었습니다. 처음엔 명령 13개를 기능 13개로
봤습니다. 실제로는 대부분이 **펌웨어 블롭의 바이트 범위를 한 패킷당 56바이트씩 옮기는
같은 동작**입니다.

`0x429130` (`0x0b` 생성기) 에서 이걸 드러낸 코드 조각:

```
cmp ebx, 6 / cmove eax, 0x30      ; 마지막(7번째) 청크만 48
al = ((ebx*8 - ebx) << 3)         ; = ebx * 56
```

두 번째 줄이 열쇠였습니다. `(x*8 - x) << 3` 은 컴파일러가 **×56** 을 시프트·감산으로
푸는 관용구입니다. 이걸 곱셈으로 되읽으면 "인덱스 × 56 = 오프셋" 이 되고, 그 순간
`[4]` 길이 / `[5..6]` 오프셋 / `[8..63]` 데이터라는 구조가 확정됩니다. `cmove` 로
마지막 청크만 48인 것도 총 길이를 알려줍니다: **56×6 + 48 = 384 = 128 × 3**.

여기서 두 가지가 따라 나옵니다.

1. 128 슬롯 × 3바이트. 키 인덱스가 109까지 올라가므로 **128 슬롯이면 전체 키 주소
   공간을 덮습니다.** 여러 명령 생성기가 128까지 도는 루프를 갖고 있는 것과 맞습니다.
2. **빈 페이로드는 무해한 질문이 아니라 "오프셋 0 에 0을 써라" 입니다.** 이걸 몰랐던
   대가가 오류 #4 입니다.

→ 명세 §2.1, §3.3

### 2.4 값 인코딩 — 통제 실험

사용자가 **Esc 액추에이션 하나만 다른 DB 두 개**(1.0 mm / 2.0 mm)를 만들어 줬습니다.
단일 변수 실험이라 비교하면 바로 나옵니다: 50 과 100.

여기서 점 두 개로 멈추지 않은 게 중요했습니다. 두 점은 `카운트 = mm × 50` 과
`카운트 = mm × 50 + c` 를 구별하지 못합니다. 세 번째 점 — 공장 기본값
`global_key_actuation = 75` 가 UI 상 1.5 mm — 이 원점을 지나는 직선을 확정하고
**오프셋 항을 죽였습니다.** 1 카운트 = 0.02 mm.

→ 명세 §4.1

### 2.5 아날로그 이벤트 — 불변량 교차검증

Esc / A / Space 를 각각 한 번 눌렀다 뗀 **16개 샘플**로 필드를 확정했습니다. 방법은
후보 필드마다 "무엇에 대해 불변인가" 를 묻는 것입니다.

| 관측된 불변성 | 따라 나오는 의미 |
|---------------|------------------|
| 모든 키·모든 깊이에서 동일 | `[14..15]` = 총 스트로크 (설정값이 아니라 상수) |
| 한 키 안에서 동일, 키끼리 다름 | `[18..19]` = 저장된 캘리브레이션 기준 ADC |
| 깊이에 단조 감소 | `[16..17]` = 현재 ADC |
| 안 눌림 0, 바닥 200 | `[7]` = 선형화된 깊이 |

`[7]` 이 **설정과 같은 단위**라는 게 결정타였습니다. 200 × 0.02 = **4.00 mm 정확히**.
DB 에서 독립적으로 얻은 0.02 mm 스케일과 하드웨어에서 얻은 카운트가 같은 단위로
떨어졌습니다 — 서로 무관한 두 출처가 한 점에서 만나는 건 우연이기 어렵습니다.
(부수적으로, 이전에 3.5 mm 로 가정했던 총 스트로크가 여기서 고쳐졌습니다.)

`[4..5]` 와 `[7]` 이 왜 **둘 다** 있는지도 여기서 설명됩니다. `[4..5]` / ADC 델타의
비율이 키마다 다릅니다 (Esc 1.151, A 1.371, Space 1.135). 즉 `[4..5]` 는 자속에
선형이고 거리에는 비선형이며, `[7]` 은 그걸 실제 이동량으로 펴 놓은 값입니다.
홀 센서의 물리와 맞습니다 — 자속은 거리에 대해 급격히, 비선형으로 떨어지니까요.

→ 명세 §3.2

### 2.6 61키 커버리지 — 부정 결과가 가장 정보량이 많았다

사용자가 **모든 키를 하나씩** 눌렀습니다. 결과: 53개는 usage 를 보고하고 8개는 안 함.

`0x00` 이 버그가 아니라는 추론이 여기서 나왔습니다. **HID 는 수정자를 키코드 배열이
아니라 첫 바이트 비트마스크로 보고합니다.** 그러니 수정자에게는 보고할 키코드 배열
usage 가 애초에 없고, 펌웨어는 그 자리에 `0x00` 을 넣습니다. Fn 이 `0x01` 인 것도
같은 이유입니다 — Fn 은 HID 키가 아니라 레이어 키입니다. 사용자가 "Fn1키는 0x01,
그 외는 0x00" 이라고 확인해 준 게 이 추론을 갈랐습니다.

그래서 **조합 식별자**가 필요해졌습니다. 8개를 전부 측정해 `센서값:기준ADC` 로 표를
만들고, 같은 센서값을 공유하는 쌍의 최소 간격(LCtrl 1880 / LShift 1888 = **8**)에서
허용 오차 **±3** 을 정했습니다.

설계상 중요한 선택 하나: **너무 멀거나 두 후보가 등거리면 엉뚱한 키를 고르지 않고
미해석으로 남깁니다.** 잘못된 키 라벨은 빈 라벨보다 나쁩니다 — 조용히 이후 모든 측정을
오염시키기 때문입니다. 같은 이유로 모니터에서 샘플을 조용히 버리던 코드도 고쳤습니다.
"보드가 안 보낸다" 와 "우리가 매핑을 못 한다" 가 구별되지 않으면 디버깅이 불가능합니다.

→ 명세 §3.2 하위 절

## 3. 실제로 효과가 있었던 방법

- **한 번에 한 변수.** DB 두 개 비교(§2.4)가 가장 값싸고 확실한 실험이었습니다.
- **불변량으로 필드 식별**(§2.5). 값을 해석하려 하지 말고, 무엇에 대해 변하지 않는지를
  묻는 것.
- **두 출처가 만나는 지점을 찾기.** 0.02 mm 는 DB 와 하드웨어 양쪽에서 독립적으로
  나왔습니다.
- **컴파일러 관용구 되읽기**(§2.3). `(x*8-x)<<3` 을 곱셈으로 복원한 게 블록 구조를
  열었습니다.
- **부정 결과를 적극적으로 받기.** 사용자의 "그 셋을 빼도 LED 가 바뀐다", "P키랑 /키가
  충돌한다", "이 8개는 인식이 안 된다" 가 각각 틀린 결론 하나씩을 죽였습니다.
  **긍정 확인보다 정보량이 많았습니다.**

## 4. 틀렸던 결론 5개

| # | 틀린 결론 | 근거였던 것 | 무엇이 잡았는가 |
|---|-----------|-------------|-----------------|
| 1 | 통신은 FEATURE 리포트 | 바이너리에 `HidD_SetFeature` 문자열 존재 | 디스어셈블 — 주소만 받아두고 **호출 0건** |
| 2 | 레이어 9개 | UI 문자열 "FN Layer 1–8" | DB `fn_layer` 는 **0–3** 뿐 |
| 3 | `key_code` = `key_index` | 추정 | DB 의 Esc = 41 = **HID usage** |
| 4 | LED 범인은 `0xa5`/`0xa7`/`0xdd` | 응답 시간이 21–54 ms 로 유독 길다 | 사용자가 그 셋을 빼고 재시도했는데 **LED 가 또 바뀜** |
| 5 | `[12..13]` 은 키별 고유 주소 | 관측한 3키에서 서로 달랐다 | 사용자: **"P키랑 /키에서 키 충돌"** |

각각의 교훈:

**#1 — 문자열은 의도가 아니다.** 이게 가장 비싼 오류였습니다. 제가 FEATURE 리포트라고
말한 탓에 캡처 시도가 엉뚱한 것을 찾고 있었을 가능성이 큽니다. 바이너리에 심볼이
있다는 건 링커가 넣었다는 뜻일 뿐입니다. **참조 횟수를 세야 합니다.**

**#2 — UI 문자열은 여러 모델이 공유한다.** 순정 드라이버 하나가 제품군 전체를
담당하므로, UI 에 있는 기능이 이 보드에 있다는 보장이 없습니다. 데이터가 우선입니다.

**#4 — 상관을 인과로 봤다.** 응답 시간이 긴 명령이 뭔가 무거운 일을 한다는 건 그럴듯한
추론이지만, 그럴듯함이 증거가 아닙니다. 그리고 진짜 이유가 밝혀졌을 때(§2.3) 그것은
개별 명령의 성질이 아니라 **모든 블록 쓰기 명령의 공통 성질**이었습니다. 즉 원인의
층위 자체를 잘못 짚고 있었습니다. 이 결과로 `SAFE_COMMANDS` 를 부작용이 관찰되지 않은
`0x01` / `0x02` / `0xa9` 세 개로 좁혔습니다.

**#5 — 표본 3개로 61개의 고유성을 주장했다.** Esc·A·Space 에서 `[12..13]` 이 서로
달랐다는 관측은 참이었지만, "그러므로 키별 고유" 는 표본 크기가 뒷받침하지 않는
일반화였습니다. 게다가 이 오류 위에 코드 버그가 하나 더 얹혀 있었습니다 — 이벤트 집계
맵의 키를 `sensorId` 로 잡아서, usage 가 정상인 P 와 `/` 까지 한 항목으로 합쳐졌습니다.
잘못된 모델과 잘못된 구현이 겹치면 증상이 원인을 가립니다.

**#6 — 부작용이 없다는 걸 확인한 게 아니라, 부작용이 안 보였을 뿐이다.** 아날로그
스트림이 "아무것도 켜지 않아도 그냥 올라온다" 고 적었습니다. 관측은 진짜였습니다 — 키를
누르면 이벤트가 올라왔습니다. 하지만 그 관측을 **순정 드라이버를 띄워 둔 채로** 했고,
드라이버가 성능 탭에서 1.9초마다 보드를 켜 주고 있었습니다. 내가 관측한 것은 보드의
기본 동작이 아니라 **다른 프로그램이 만들어 준 상태**였습니다. 정적 분석으로
`0x429f20` / `0x42cb80` 을 읽고서야 드러났습니다 (명세 §3.2).

> 교훈: "X 없이도 동작한다" 를 주장하려면 **X 를 실제로 없앤 상태에서** 봐야 합니다.
> 순정 드라이버를 완전히 종료하고, 보드를 뽑았다 꽂고, 그 다음에 관측할 것.

**#7 — 짝 중 어느 쪽이 켜기인지 정적 분석으로 정했다.** `0x429f20` 이 플래그로 `0xa9` /
`0xa8` 을 고르는 것까지는 정확히 읽었습니다. 거기서 "플래그 기본값(0)에서 나가는 쪽이
정상 경로이므로 `0xa9` 가 켜기" 라고 결론했는데 **반대였습니다** — `0xa8` 이 진입,
`0xa9` 가 해제입니다. 코드 구조는 두 명령이 **짝**이라는 것만 말해 주고, 어느 쪽이
어느 방향인지는 말해 주지 않습니다. 방향은 보드에 물어봐야 알 수 있었습니다.

> 이 오류에는 대가가 붙어 있었습니다. 잘못된 배정 위에서 "정지할 때 짝인 `0xa8` 을
> 보낸다" 는 정리 코드를 짰는데, 그것은 정지할 때마다 **캘리브레이션 모드로 들어가는**
> 코드였습니다. 방향을 틀리면 해제 경로가 진입 경로가 됩니다.

**#8 — 모드를 관찰 창구로 여겼다.** `0xa8` 을 "스트림을 켜는 스위치" 로만 봤습니다.
실제로는 키를 끝까지 누르면 **바닥 자성값을 보정하는** 모드였습니다. 즉 모니터를 켜고
키를 바닥까지 누르는 것은 읽기가 아니라 **쓰기**입니다. 드라이버가 이 모드에서만
1.9초마다 갱신을 보내는 이유도 그래야 설명됩니다.

**#9 — 안 변하는 값이라고 두 번 확인했지만, 변하는 조건을 안 만들어 봤다.**
`payload[12..13]` 을 "주소는 아니지만 키마다 고정" 으로 뒀습니다. 한 키의 모든 샘플에서
값이 같았고, 기준 ADC 도 그랬습니다. 관측은 반복까지 했으니 튼튼해 보였습니다.

빠진 것은 **그 값을 바꾸는 조작**이었습니다. 캘리브레이션을 돌리자 LCtrl 의 센서값이
`0x0805` → `0x0806` 으로 바뀌었고, 그 자리는 LAlt 의 것이어서 **LCtrl 이 LAlt 로
해석되었습니다**. 오해석은 미해석보다 나쁩니다 — 화면이 자신 있게 거짓을 말합니다.

> 교훈: "상수" 는 **관측 기간에 대한 진술**입니다. 상수라고 쓰려면 그것을 바꿀 만한
> 조작(보정·재부팅·펌웨어 갱신)을 한 번씩 해 보고 나서 써야 합니다. #6 과 같은 모양의
> 오류이고, 그때 얻은 교훈("X 를 실제로 없앤 상태에서 보라")을 다른 필드에는 적용하지
> 않았습니다.

**#10 — 정답지가 답을 가렸다.** 캘리브레이션에 흔들리지 않는 키 주소를 찾으려고, usage
로 이름을 말하는 키 53개를 정답지로 삼아 바이트마다 "한 키 안에서 고정 + 키마다 다름" 을
검사하는 도구를 만들었습니다. 논리는 맞았고, **답은 그 검사를 통과하지 못했습니다.**

`payload[2]` 는 일반 키에서 전부 같은 값입니다. 그러니 "키마다 다름" 에서 탈락하고
`중복` 으로 분류됩니다. 정작 그 바이트는 **수정자 8개에서만** 서로 다릅니다 — 찾던 것이
바로 그 8개였는데, 정답지에 그 8개가 없으니 보이지 않았습니다. 관측 데이터에는 처음부터
들어 있었고, 도구가 그것을 걸러냈습니다.

답은 결국 바이너리에서 나왔습니다 (`0x426050` 의 점프 테이블). 하드웨어 관측과 정적 분석
중 어느 쪽도 혼자서는 답을 못 줬습니다.

> 교훈: 분석 도구의 필터는 **가설**입니다. "주소라면 모든 키에서 달라야 한다" 는 가설이
> 참이라고 가정하고 필터를 걸었고, 실제 답은 "찾는 대상 안에서만 다르다" 였습니다.
> 후보를 지우는 도구를 만들 때는, 그 도구가 지운 것을 한 번은 봐야 합니다.

**#11 — 그럴듯한 원인을 찾자마자 원인이라고 불렀다.** "보정 전에는 감지가 안 된다" 를
듣고 `parseKeyEvent` 가 총 스트로크 0 인 이벤트를 버리는 코드를 발견했습니다. 보정 전
보드가 스트로크를 0 으로 보고한다면 증상이 정확히 설명되고, 실제로 그 코드는 버그였습니다.
**그래서 원인이라고 단정했고, 아니었습니다.** 고친 뒤에도 증상이 그대로였습니다.

진짜 원인은 `0x06` 의 플래그 바이트였습니다 (명세 §3.2). 두 개가 겹쳐 있었을 뿐입니다 —
버그 하나와 빠진 단계 하나.

> 교훈: 증상을 설명하는 버그를 찾았다는 것은 **그 버그가 원인이라는 증거가 아닙니다.**
> 특히 코드에서 찾은 버그는 언제나 그럴듯해 보입니다. 고친 다음 증상이 사라지는 것을
> 확인하기 전까지는 "원인 후보" 라고 불러야 합니다. #4 와 같은 오류(상관을 인과로)이고,
> 이번에는 내가 그것을 사용자에게 단정형으로 보고했습니다.

**#12 — 관측한 코드를 그대로 베끼면서, 그 코드가 어느 모드의 것인지 안 봤다.** 순정
드라이버가 `0xa8` 을 1.9초마다 재전송하는 것을 보고 "이 모드는 갱신하지 않으면 꺼진다" 로
읽고, 모니터에 1.5초 주기 재전송을 넣었습니다. 재전송 코드는 실재했고 주기도 정확했습니다.

놓친 것은 **그 코드에 걸린 조건**입니다. `0x42cb1a` 가 `[this+0x541fc] != 0` 을 요구하므로
그 루프는 **캘리브레이션 모드에서만** 돕니다. 일반 관찰에서는 `0xa8` 한 번이면 걸쇠처럼
유지됩니다. 조건문 한 줄을 기능이 아니라 배경으로 읽은 결과, 우리가 만든 모니터는:

- 켜는 동안 타이핑을 죽였고 (→ "모니터 실행 중 타이핑 불가" 를 **사양이라고 문서에 적었습니다**)
- 모니터링 내내 재보정을 돌려서 기준 ADC 와 센서값을 계속 움직였습니다

즉 오류 #8·#9 에서 "캘리브레이션이 식별자를 깨뜨린다" 며 관측했던 표류의 상당 부분은
**우리 코드가 만든 것**이었습니다. 남의 버그를 찾다가 자기 버그를 관측하고, 그것을 펌웨어의
성질로 기록했습니다.

> 교훈: 바이너리에서 베낀 동작에는 **그것이 실행되는 조건**까지 함께 베껴야 합니다.
> `if` 를 빼고 본문만 가져오면, 특수 모드의 동작이 기본 동작이 됩니다.

**패턴:** 12개 중 8개가 **단일 증거로 내린 결론**입니다. §3 처럼 두 출처를 교차검증한
결론은 지금까지 하나도 틀리지 않았습니다. #6 은 여기에 한 겹을 더합니다 — 관측이
정확해도 **관측 환경이 결론의 일부**입니다. #7 과 #8 은 또 한 겹입니다: 바이너리는
**구조**를 정확히 알려주지만 (두 명령이 짝이다, 주기가 1.9초다), 그 구조에 **어느 방향**
과 **어떤 의미**가 붙는지는 알려주지 않습니다. 방향과 의미는 보드만 압니다.

## 5. 남은 것 — 그리고 각각을 가르는 실험

명세 §9 의 목록에, **무엇을 하면 갈리는지**를 붙입니다.

| 미해결 | 결정적 실험 | 비용 |
|--------|-------------|------|
| 명령이 키를 usage 로 지정하나 `key_index` 로 지정하나 | Esc(41 vs 16) 또는 A(4 vs 49) 를 한 번 관측 | 관측 1회 |
| `0x02` 가 RAM 적용인가 플래시 저장인가 | 설정을 쓰고 **전원을 뽑았다 꽂아** 유지되는지 본다 | 실험 1회 |
| 이벤트 `payload[8]` 의 의미 | 한 키만 래피드 트리거를 켜고 `[8]` 의 거동 변화를 본다 | 실험 1회 |
| `[12..13]` 의 정체 | 캘리브레이션 전후로 값이 바뀌는지 본다 | ⚠ 식별표가 어긋남 |
| **설정 쓰기 명령의 데이터 배치** | §5.1 | 큼 |

`[12..13]` 실험은 성공해도 부작용이 있습니다. 재캘리브레이션은 기준 ADC 를 바꾸므로
`fingerprints.ts` 의 8개 항목이 어긋나고, 이벤트 탭에서 다시 연결해야 합니다.
급하지 않은 질문이라 미뤄 두는 게 맞습니다.

### 5.1 쓰기 배치 — 캡처 없이 갈 수 있는 길 (제안, 미검증)

이게 마지막 큰 벽이고, 지금까지의 방법이 전부 막히는 지점입니다. `[bin]` 은 어떤
블롭에 쓰는지까지만 알려주고 (§2.1 의 크기 표), `[hw]` 는 응답이 에코라서 아무것도
알려주지 않고, `0xa9` 는 상수만 돌려줍니다. **읽어서 확인할 채널이 없습니다.**

그런데 우회로가 하나 있습니다. **액추에이션 포인트는 관측 가능합니다.**

보드는 아날로그 이벤트를 올려보내면서 **동시에 평범한 HID 키보드로도 동작합니다.**
그러니 키를 아주 천천히 누르면서 브라우저에서 두 가지를 같이 기록할 수 있습니다.

1. 아날로그 이벤트의 `[7]` — 0.02 mm 단위 실제 깊이, 연속적으로
2. `keydown` 이 발생한 순간

**`keydown` 이 뜬 시점의 `[7]` 값이 그 키의 실효 액추에이션 포인트입니다.** 정밀도는
이벤트 샘플 간격만큼입니다. 즉 캡처 장비 없이, 보드 스스로가 자기 설정을 읽어주는
**오라클**이 생깁니다.

이게 있으면 쓰기 배치를 맹목적으로가 아니라 **측정하면서** 찾을 수 있습니다.
후보 배치로 한 키의 액추에이션을 눈에 띄게 다른 값(예: 0.5 mm ↔ 3.5 mm)으로 쓰고,
위 방법으로 실측해 움직였는지 본다. 움직였으면 오프셋을 맞춘 것입니다.

⚠ **아직 시도하지 않았습니다.** 그리고 §2.3 을 감안하면 규율이 필요합니다.

- 한 번에 **명령 하나, 오프셋 하나**만 건드린다
- 조명 블롭 근처를 피한다 (오류 #4 로 이미 한 번 덮어썼습니다)
- 시작 전에 순정 드라이버로 프로파일을 저장해 **복구 경로를 확보**한다
- 순정 드라이버에서 조명 프로파일을 다시 적용하면 LED 는 복구됩니다

이건 명세가 아니라 **가설**입니다. 검증되면 protocol.md 로 옮깁니다.

## 6. 결론이 코드의 어디에 살아 있는가

| 결론 | 구현 위치 |
