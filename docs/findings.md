# Raven61 추론 기록

[protocol.md](./protocol.md) 는 **무엇이 사실인가**를 적습니다.
[reverse-engineering.md](./reverse-engineering.md) 는 **어떻게 캡처하는가**를 적습니다.

이 문서는 **어떻게 알아냈는가** 를 적습니다 — 각 결론이 무슨 증거에 얹혀 있고, 얼마나
믿을 수 있고, 어떤 결론이 틀렸다가 무엇에 의해 잡혔는지. 사실 자체는 여기서 반복하지
않고 명세의 절을 가리킵니다.

## 0. 출발점

순정 드라이버는 **PE32/x86 MFC C++ 윈도우 네이티브 exe** 입니다. Electron 이 아니라서
자바스크립트를 읽는 손쉬운 길이 없었습니다.

그리고 **USB 캡처가 전부 실패했습니다.** 이게 이 프로젝트의 방법론을 결정했습니다.
캡처가 됐다면 와이어 포맷을 그냥 읽으면 끝이었을 일을, 캡처 없이 세 갈래로 우회해야
했습니다.

| 경로 | 무엇을 주는가 |
|------|---------------|
| **정적 분석** — 임포트 표, IAT 호출 지점, 디스어셈블 | 드라이버가 **보내려고 의도한** 형식 |
| **순정 데이터 파일** — SQLite DB, 레이아웃 XML | 설정 **값**의 의미와 스케일 |
| **보드에 직접 질문** — 웹 드라이버의 프로버·이벤트 탭 | 보드가 **실제로 하는** 행동 |

세 경로가 각각 답할 수 없는 것이 있고, 그 공백이 지금 미해결로 남은 것과 정확히
일치합니다 (§5).

## 1. 증거 등급

명세의 `[bin]` `[db]` `[xml]` `[hw]` `[cap]` 태그는 출처 표기이자 **증명력의 등급**입니다.

| 등급 | 증명하는 것 | 증명하지 못하는 것 |
|------|-------------|--------------------|
| `[bin]` 정적 분석 | 드라이버 코드가 무엇을 만드는가 | 그 코드가 실행되는가 (→ 오류 #1) |
| `[db]` 순정 DB | 드라이버 내부 데이터 모델 | 그 모델이 와이어에 그대로 나가는가 (→ §5) |
| `[xml]` 레이아웃 | 키 주소와 물리 위치의 대응 | 명령이 그 주소를 쓰는가 |
| `[hw]` 하드웨어 관측 | 보드가 실제로 무엇을 보내는가 | 보드가 무엇을 **받는지** — 응답이 에코라서 |
| `[cap]` USB 캡처 | 와이어 포맷 그 자체 | **확보 실패 — 이게 남은 공백의 원인** |

핵심은 이렇습니다. `[bin]` 은 **의도**를, `[hw]` 는 **결과**를 봅니다. 읽기 방향은
`[hw]` 로 완전히 검증됐고, **쓰기 방향은 어느 등급으로도 검증할 수 없습니다** — 명령
응답이 요청의 에코일 뿐이라 보드가 무엇을 이해했는지 알려주지 않기 때문입니다.

## 2. 추론 사슬

### 2.1 전송 계층 — "문자열이 있다" 가 아니라 "몇 번 호출되는가"

사슬: 문자열 → 임포트 표 → IAT 호출 지점 → 송수신 헬퍼 디스어셈블.

결정적이었던 것은 `HidD_SetFeature` **문자열의 존재가 아니라 참조 횟수**였습니다.
`GetProcAddress` 로 받은 주소가 전역 `0x5a1f98` 에 저장되는 참조가 **1건, 호출 0건**.
`CH375*` 임포트 8개도 전부 호출 0건인 죽은 코드였습니다.

그 다음에 `0x45a940` 이 **모든 명령이 공통으로 쓰는 단 하나의 송수신 헬퍼**라는 걸
찾은 게 표를 열었습니다. 호출 지점 52곳을 모으고 각 호출자에서 명령 바이트가
즉시값(immediate)으로 들어가는 걸 읽으면 명령 표가 나옵니다 — `tools/bin/commands.py`
가 하는 일입니다.

→ 명세 §1, §3

### 2.2 프레임 — 루프의 *모양*이 알고리즘을 준다

체크섬 루프 `0x45a9a5`–`0x45a9dc` 는 10회 × 6바이트로 펼쳐진(unrolled) 형태입니다.
루프 횟수와 스트라이드만 읽어도 **범위 60바이트**가 나오고, 누산 방식에서 **단순 8비트
합**이 나옵니다. 그리고 결과를 `[esi+4]` 에 저장하므로 **체크섬은 자기 다음 바이트부터
끝까지를 덮습니다** — 자기 자신은 포함하지 않습니다. 구현할 때 틀리기 쉬운 부분이라
코드에서 직접 읽어낸 값이 중요했습니다.

응답이 **요청의 에코**(`payload[0]` 만 `0xAA`)라는 건 하드웨어에서 확인했고, 이게 왜
중요한지는 §1 마지막 문단과 같습니다: **명령의 성공 여부를 알려주는 채널이 없다.**
초기 스윕에서 13개 명령이 전부 "ACK" 를 돌려준 건 전부 이해했다는 뜻이 아니라
**아무 의미도 없었다**는 뜻이었습니다.

→ 명세 §2, §3.1

### 2.3 재구성 — 13개 기능이 아니라 하나의 블록 전송

이게 이 프로젝트에서 가장 큰 관점 전환이었습니다. 처음엔 명령 13개를 기능 13개로
봤습니다. 실제로는 대부분이 **펌웨어 블롭의 바이트 범위를 한 패킷당 56바이트씩 옮기는
같은 동작**입니다.

`0x429130` (`0x0b` 생성기) 에서 이걸 드러낸 코드 조각:

```
cmp ebx, 6 / cmove eax, 0x30      ; 마지막(7번째) 청크만 48
al = ((ebx*8 - ebx) << 3)         ; = ebx * 56
```

두 번째 줄이 열쇠였습니다. `(x*8 - x) << 3` 은 컴파일러가 **×56** 을 시프트·감산으로
푸는 관용구입니다. 이걸 곱셈으로 되읽으면 "인덱스 × 56 = 오프셋" 이 되고, 그 순간
`[4]` 길이 / `[5..6]` 오프셋 / `[8..63]` 데이터라는 구조가 확정됩니다. `cmove` 로
마지막 청크만 48인 것도 총 길이를 알려줍니다: **56×6 + 48 = 384 = 128 × 3**.

여기서 두 가지가 따라 나옵니다.

1. 128 슬롯 × 3바이트. 키 인덱스가 109까지 올라가므로 **128 슬롯이면 전체 키 주소
   공간을 덮습니다.** 여러 명령 생성기가 128까지 도는 루프를 갖고 있는 것과 맞습니다.
2. **빈 페이로드는 무해한 질문이 아니라 "오프셋 0 에 0을 써라" 입니다.** 이걸 몰랐던
   대가가 오류 #4 입니다.

→ 명세 §2.1, §3.4

### 2.4 값 인코딩 — 통제 실험

사용자가 **Esc 액추에이션 하나만 다른 DB 두 개**(1.0 mm / 2.0 mm)를 만들어 줬습니다.
단일 변수 실험이라 비교하면 바로 나옵니다: 50 과 100.

여기서 점 두 개로 멈추지 않은 게 중요했습니다. 두 점은 `카운트 = mm × 50` 과
`카운트 = mm × 50 + c` 를 구별하지 못합니다. 세 번째 점 — 공장 기본값
`global_key_actuation = 75` 가 UI 상 1.5 mm — 이 원점을 지나는 직선을 확정하고
**오프셋 항을 죽였습니다.** 1 카운트 = 0.02 mm.

→ 명세 §4.1

### 2.5 아날로그 이벤트 — 불변량 교차검증

Esc / A / Space 를 각각 한 번 눌렀다 뗀 **16개 샘플**로 필드를 확정했습니다. 방법은
후보 필드마다 "무엇에 대해 불변인가" 를 묻는 것입니다.

| 관측된 불변성 | 따라 나오는 의미 |
|---------------|------------------|
| 모든 키·모든 깊이에서 동일 | `[14..15]` = 총 스트로크 (설정값이 아니라 상수) |
| 한 키 안에서 동일, 키끼리 다름 | `[18..19]` = 저장된 캘리브레이션 기준 ADC |
| 깊이에 단조 감소 | `[16..17]` = 현재 ADC |
| 안 눌림 0, 바닥 200 | `[7]` = 선형화된 깊이 |

`[7]` 이 **설정과 같은 단위**라는 게 결정타였습니다. 200 × 0.02 = **4.00 mm 정확히**.
DB 에서 독립적으로 얻은 0.02 mm 스케일과 하드웨어에서 얻은 카운트가 같은 단위로
떨어졌습니다 — 서로 무관한 두 출처가 한 점에서 만나는 건 우연이기 어렵습니다.
(부수적으로, 이전에 3.5 mm 로 가정했던 총 스트로크가 여기서 고쳐졌습니다.)

`[4..5]` 와 `[7]` 이 왜 **둘 다** 있는지도 여기서 설명됩니다. `[4..5]` / ADC 델타의
비율이 키마다 다릅니다 (Esc 1.151, A 1.371, Space 1.135). 즉 `[4..5]` 는 자속에
선형이고 거리에는 비선형이며, `[7]` 은 그걸 실제 이동량으로 펴 놓은 값입니다.
홀 센서의 물리와 맞습니다 — 자속은 거리에 대해 급격히, 비선형으로 떨어지니까요.

→ 명세 §3.2

### 2.6 61키 커버리지 — 부정 결과가 가장 정보량이 많았다

사용자가 **모든 키를 하나씩** 눌렀습니다. 결과: 53개는 usage 를 보고하고 8개는 안 함.

`0x00` 이 버그가 아니라는 추론이 여기서 나왔습니다. **HID 는 수정자를 키코드 배열이
아니라 첫 바이트 비트마스크로 보고합니다.** 그러니 수정자에게는 보고할 키코드 배열
usage 가 애초에 없고, 펌웨어는 그 자리에 `0x00` 을 넣습니다. Fn 이 `0x01` 인 것도
같은 이유입니다 — Fn 은 HID 키가 아니라 레이어 키입니다. 사용자가 "Fn1키는 0x01,
그 외는 0x00" 이라고 확인해 준 게 이 추론을 갈랐습니다.

그래서 **조합 식별자**가 필요해졌습니다. 8개를 전부 측정해 `센서값:기준ADC` 로 표를
만들고, 같은 센서값을 공유하는 쌍의 최소 간격(LCtrl 1880 / LShift 1888 = **8**)에서
허용 오차 **±3** 을 정했습니다.

설계상 중요한 선택 하나: **너무 멀거나 두 후보가 등거리면 엉뚱한 키를 고르지 않고
미해석으로 남깁니다.** 잘못된 키 라벨은 빈 라벨보다 나쁩니다 — 조용히 이후 모든 측정을
오염시키기 때문입니다. 같은 이유로 모니터에서 샘플을 조용히 버리던 코드도 고쳤습니다.
"보드가 안 보낸다" 와 "우리가 매핑을 못 한다" 가 구별되지 않으면 디버깅이 불가능합니다.

→ 명세 §3.2 하위 절

### 2.7 슬롯 매핑 — 설정을 신호로 쓴 실험

키별 성능 블록은 읽히는데 **어느 슬롯이 어느 키인지** 알 수 없었습니다. 레이아웃에서
계산하려는 시도가 세 번 실패한 뒤 (오류 #13), 방향을 뒤집었습니다: 계산하지 말고
**보드가 답을 말하게** 만들자.

방법은 순정 드라이버를 신호 발생기로 쓰는 것입니다. **키보드 행마다 다른 동작 지점**을
넣고 블록을 읽으면, 슬롯의 값이 그 슬롯의 행을 알려줍니다.

```
행 0 (Esc–Backspace)  0.10 mm =   5 카운트
행 1 (Tab–\)          0.70 mm =  35
행 2 (Caps–Enter)     1.30 mm =  65
행 3 (Shift–Shift)    1.80 mm =  90
행 4 (Ctrl–Fn)        2.60 mm = 130
```

읽어 보니 슬롯별 값의 개수가 **14 / 14 / 13 / 12 / 8** — 실제 행의 키 수와 정확히
일치했습니다. 이 한 번의 실험이 세 가지를 동시에 줬습니다:

1. **슬롯 → 행** 이 전부 확정됐습니다 (명세 §4.6 의 표).
2. 그 배치가 **어떤 규칙으로도 계산되지 않는다**는 것이 확인됐습니다. `slot mod 8`,
   `slot div 8`, `row_col`, 레이아웃 순서 — 전부 이 배치를 만들지 못합니다.
   부정 결과지만 §2.6 처럼 정보량이 가장 컸습니다: "계산하지 말고 물어봐라".
3. 정적 테이블 검색의 **정답지**가 생겼습니다. 바이너리 전체를 바이트·워드 폭으로
   훑으면서 "61칸 중 몇 칸이 이 행 제약을 만족하는가" 를 점수로 매길 수 있었고,
   **30칸 이상 맞는 창이 하나도 없어** 정적 테이블이 없다는 것을 확정했습니다.

덤으로 레코드 해독도 독립 검증됐습니다. 하단행 레코드 `a6 01 81 00 33 00 3d 00` 이
액추에이션 130 = **2.60 mm**, RT 누름 52 = **1.04 mm**, RT 뗌 62 = **1.24 mm** 로
해독되고, 순정 화면에 찍힌 숫자와 그대로 같았습니다. 인코더·디코더 대조(§2.3 방식)로
얻은 형식이 실제 값에서도 맞는다는 확인입니다.

> 일반화할 수 있는 기법입니다. **쓰기 채널이 있는 필드는 신호로 쓸 수 있습니다.**
> 미지의 블록에서 색인 체계를 찾을 때, 순정 UI 로 구조화된 패턴(행별·열별·키별)을
> 심어 놓고 읽으면 색인이 드러납니다. 값 자체가 이미 해독되어 있어야 하고, 순정에서
> 그룹 단위로 설정할 수 있어야 합니다 — 둘 다 여기서는 만족됐습니다.
>
> 더 조여야 하면 **키마다 다른 값**을 넣으면 슬롯이 키 단위로 확정됩니다. 순정에서
> 61번 선택해야 하므로 행 단위로 먼저 좁히는 것이 실용적입니다.

### 2.8 설정 탭 — 값의 의미는 드라이버가 콤보 박스를 채우는 코드에 있다

폴링 레이트와 디바운스는 **바이트 위치가 먼저 확정되고 값의 의미가 한참 뒤에 붙은**
사례입니다. `payload[12]` 하위 4비트가 `reporte_rate` 라는 것은 `0x429300` 이 같은
바이트를 `& 0x0f` 로 되읽어 UI 에 올리는 것으로 이미 알고 있었지만, **1 이 몇 Hz 인지는
그 코드 어디에도 없었습니다.** DB 에는 `1` 과 `4` 라는 값만, 언어 파일에는
"8000Hz / 4000Hz / 2000Hz / 1000Hz" 라는 문자열만 있었고, 둘을 잇는 것이 없었습니다.

이은 것은 **콤보 박스를 채우는 코드**입니다 (`0x4443ef`–`0x444527`). MFC 의
`AddString` 호출마다 언어 문자열 id 와 그 항목의 값이 나란히 스택에 밀립니다:

```
push 0; push 0; push 1 ; … ; push 0x50   ; AddString   ; 값 1 ↔ 문자열 80 "8000Hz"
push 0; push 0; push 2 ; … ; push 0x51   ; AddString   ; 값 2 ↔ 81 "4000Hz"
```

같은 함수 안에서 `tick_rate`(0/1/2)와 `debounce_level`(0/1/2)도 같은 모양으로 나오고,
**셋 중 폴링 레이트만 1 부터 시작한다**는 비대칭이 이 숫자가 목록 인덱스가 아니라
값이라는 증거가 됩니다. 순정 DB 가 `1` 과 `4` 만 갖는 것 — 그 범위의 양 끝 — 이 독립적인
교차확인입니다.

한계도 같이 적어 둡니다. **폴링 레이트를 바꾸는 캡처는 뜨지 못했습니다.** 근거는
`[bin]` 하나뿐이고, 게다가 이 필드는 쓰기 검증(§5.1)의 되읽기가 정상적으로 실패할 수
있는 유일한 필드입니다 — 레이트가 바뀌면 보드가 USB 를 다시 잡을 수 있기 때문입니다.

`debounce_level` 은 여기서 **멈춘 지점**입니다. High / Medium / Low 라는 이름까지는
나오지만 **그것이 몇 ms 인지는 드라이버에도 펌웨어에도 없습니다.** 그래서 이 앱은 이름과
원본 값만 보여줍니다. 없는 숫자를 만들어 붙이는 것이 여기서는 가장 나쁜 선택입니다.

### 2.9 "펌웨어 버전" 은 없었다 — 있는 것은 빌드 날짜다

설정 탭에 펌웨어 버전을 띄우려던 것이 출발이었는데, **버전 번호라는 것이 이 보드에
존재하지 않았습니다.** 순정 드라이버에도 버전을 묻는 명령이 없어서 (§3 의 명령 표는
드라이버의 호출 지점에서 뽑은 것이라 애초에 나올 수가 없었습니다) 펌웨어 쪽에서
찾았습니다 — `0xaa` 를 찾을 때와 같은 경로입니다.

분배표(`0x157b0`)에서 아직 손대지 않은 항목들을 하나씩 디스어셈블하다 `0x03` →
`0x667c` 가 나왔고, 핸들러가 하는 일이 그대로 답이었습니다: 플래시의 문자열 셋을
응답 버퍼로 복사하며 쉼표로 잇고 길이를 `payload[4]` 에 씁니다. 이미지에서 그 주소를
읽으면 `HALL_HS_USB_KB` · `Nov 13 2024` · `11:05:59` — **빌드 이름과 컴파일러의
`__DATE__` / `__TIME__`** 입니다. 이미지 전체에서 버전처럼 생긴 문자열은 이 하나뿐이라,
없는 것이 확인된 셈이기도 합니다.

> 이것도 §2.6 과 같은 종류의 결과입니다. **찾던 것이 없다는 사실 자체가 답**이고,
> UI 에서 "버전" 이라고 부르지 않기로 한 근거입니다. 같은 날 빌드된 두 펌웨어는
> 구분되지 않는다는 한계까지 화면에 적혀 있습니다.

핸들러를 읽은 김에 부작용도 같이 확정됐습니다. 쓰는 경로가 없고 응답 버퍼에만
저장하므로 `0x03` 은 `0xaa` 와 같은 근거로 `SAFE_COMMANDS` 에 들어갔습니다 — §3.4 의
"빈 페이로드도 쓰기다" 가 적용되지 않는 몇 안 되는 명령입니다.

### 2.10 공장 초기화 — "무엇이 남는가" 를 먼저 알아야 버튼을 만들 수 있다

`0xee` 가 공장 초기화라는 것은 처음부터 알고 있었습니다. 그런데 **버튼을 만들려면 그
정도로는 부족합니다.** 화면에 "모든 설정이 지워집니다" 라고 쓰려면 무엇이 지워지는지
알아야 하고, 더 중요하게는 **무엇이 지워지지 않는지**를 알아야 합니다. 캘리브레이션까지
날아간다면 그건 다시 학습시켜야 하는 것이고, 설정만 날아간다면 다시 넣으면 되는
것입니다. 둘은 사용자에게 전혀 다른 결정입니다.

핸들러부터 봤더니 **아무것도 지우지 않았습니다** — 플래그 한 바이트를 세우고 끝입니다
(`0x76c6`). 그래서 ACK 가 즉시 돌아오고, **ACK 는 초기화 성공의 증거가 아닙니다.**
플래그를 읽는 쪽(`0x1450c`)을 따라가서야 실제 목록이 나왔습니다: 전역 설정 · 키맵 ·
키별 성능은 이미지 안의 기본값 표에서 복사되고 조명 블롭은 0 으로 채워지는데,
**`0x20300` 은 그 목록에 없습니다.** 보정 표가 사는 주소입니다 (§3.3).

> 이 한 줄이 UI 문구의 절반을 결정했습니다. "키 캘리브레이션은 남습니다" 를 근거와 함께
> 적을 수 있게 됐고, 그 근거는 추측이 아니라 **쓰지 않는다는 것을 확인한 코드**입니다.

부수적으로 §2.8 의 폴링 레이트 짝짓기가 한 번 더 지지받았습니다. 기본값 표
(`0x175b4`)의 `reporte_rate` 가 **4** 이고, 그 표의 앞 4바이트 `50 00 aa bb` 는 §4.8 이
실측으로 적어 둔 헤더와 정확히 같습니다 — 즉 이 표의 오프셋 해석은 맞습니다. 4 가
1000 Hz 라면 공장 기본값으로 자연스럽고, 4000 Hz 라면 덜 자연스럽습니다. 드라이버
콤보 박스와 **완전히 다른 경로**에서 나온 증거라 값이 있습니다.

한계는 그대로입니다. 실제 보드에서 `0xee` 를 보낸 적은 없고, 위는 전부 정적 분석입니다.
그래서 앱은 되읽은 값이 기본값 표와 다르면 **다르다고만** 말하고 실패로 단정하지 않으며,
아예 답이 없으면 "읽지 못함" 으로 보고합니다 — 6초가 모자랐을 수도 있고 보드가 USB 를
다시 잡는 중일 수도 있는데, 방금 자기를 지운 보드에게 "실패했다" 고 말하는 쪽이 둘 중
더 나쁜 오답입니다.

### 2.11 프로파일 질문 — 초기화 루틴이 플래시 지도를 통째로 준다

질문은 "순정 UI 에 없는 프로파일 기능이 펌웨어에는 있는가" 였습니다. 명령을 하나씩 열어
보는 접근으로는 오래 걸릴 일이었는데, **31개 핸들러가 거의 전부 같은 함수**라는 걸 알고
나니 한 번에 끝났습니다.

읽기 핸들러는 전부 이 모양입니다:

```
payload[5..6] → 오프셋,  payload[4] → 길이
for i: payload[8+i] = *(베이스 + 오프셋 + i)
```

서로 다른 것은 **베이스 주소 상수 하나뿐**입니다. 그래서 31개에서 그 상수만 뽑는
스크립트를 돌리면 설정 영역 전체가 한 장으로 나옵니다 (명세 §3.8). 여기에 공장 초기화
루틴(`0x14500`)을 겹치면 **크기까지** 확정됩니다 — 초기화가 각 주소에 몇 바이트를 쓰는지
그대로 적혀 있으니까요.

그 지도가 질문에 바로 답했습니다. **어느 블록도 여러 벌이 아닙니다.** 프로파일이
있으려면 키맵이든 성능이든 N 벌이 있어야 하는데 전부 1벌이고, 키맵만 512바이트 슬롯
2장입니다. 이 시점에서 "프로파일은 없다" 가 거의 확정됐습니다.

그 다음이 흥미로웠습니다. 키맵 조회식(`0x885e`)이

```
0x20b00 + 레이어 * 512 + 슬롯 * 3
```

이고, 레이어 바이트를 쓰는 동작 코드가 **네 개의 값(0·1·2·3)** 을 넣습니다 — 즉
**코드는 2프로파일 × 2레이어로 쓰여 있는데 플래시는 2장뿐**입니다. 레이어 2·3 의 주소를
계산해 보니 각각 RGB 영역과 매크로 영역이었습니다. 상위 모델용 SDK 를 공유하면서 이
모델에서는 할당하지 않은 것으로 보입니다.

**교훈은 §2.3 의 반복입니다.** 명령을 기능 31개로 보면 31번 조사해야 하지만, 하나의
블록 전송으로 보면 상수 31개를 뽑는 일이 됩니다. 그리고 이번에는 **초기화 루틴이
정답지 역할을 했습니다** — 어느 주소에 무엇을 몇 바이트 쓰는지가 한 함수에 모여 있는
곳이라, 핸들러에서 뽑은 베이스와 교차검증이 됐습니다. 실제로 그 교차검증에서 이전 판
§3.7 표의 뒤바뀐 두 줄이 잡혔습니다 (오류 #21).

### 2.12 리맵 — 목록이 아니라 **인코더**를 찾아야 했다

키 매핑을 붙이려면 두 가지가 필요합니다. 보드가 무엇을 받아들이는가, 그리고 순정이
무엇을 보내는가. 첫 번째만 보면 반쪽입니다 — 펌웨어는 타입 바이트 열몇 개를 디코드하는데
그중 어느 것을 순정 UI 가 실제로 만들어 내는지는 펌웨어에 적혀 있지 않습니다.

처음 접근은 목록 쪽이었습니다. 바이너리에서 `Vol+`, `Web Home`, `RGB Mode+` 같은
와이드 문자열이 한 덩어리로 나오니까 카테고리는 바로 보입니다. **그런데 이름만으로는
아무것도 못 씁니다.** 필요한 건 각 이름이 어떤 값과 짝지어지는가입니다.

그 짝은 목록을 채우는 코드에 있었습니다 (`0x414700`–`0x415b00`). 항목마다
`push <문자열>` 과 `push <값>` 이 나란히 있어, 문자열 VA 를 역참조하면서 스캔하면
카테고리 여섯 개가 값까지 통째로 나옵니다. `Player 0x183`, `Vol+ 0xe9` … 컨슈머 페이지
usage 였습니다.

**결정적인 함수는 그 다음이었습니다.** 목록의 값은 DB 에 들어가는 `macro_value` 이지
와이어 바이트가 아닙니다. 둘을 잇는 것이 `0x429f80` — `t_key_macro_data` 한 행을
3바이트로 바꾸는 인코더이고, 분기 하나하나가 곧 "순정이 만들 수 있는 레코드의 전부"
입니다. `macro_type` 6 → `0x30`, 5 → `0x20`/`0x21`, 3 → `0x70`, 14–19 → `0x90`–`0x95`.
마우스 항목이 왜 여덟 개인데 타입은 둘뿐인지도 여기서 나옵니다 — 더블클릭은 좌클릭
마스크에 `code = 1`, 휠은 별도 타입에 부호 있는 한 칸입니다.

교차검증은 세 방향이었습니다:

1. 인코더가 만드는 타입 ↔ 펌웨어 누름 시점 분배(`0x9ec6`)가 받는 타입
2. 그 타입 ↔ **부팅 검사(`0xa7ae`)가 유효하다고 인정하는 목록** — 슬롯 0 의 타입이
   그 목록에 없으면 펌웨어가 키맵 두 장을 공장 표에서 다시 깝니다. 유효값 목록을
   펌웨어가 자기 입으로 열거해 주는 셈입니다
3. `0xf0` 동작 코드 ↔ 조명 함수 호출(`0x812c` → `0xf984`·`0xfad2`·`0xfbc2`·`0xfc34`)

세 번째가 없었으면 `0x2b`–`0x3e` 가 조명이라는 것을 목록의 이름만 믿고 적었을 겁니다.

**쓰기 절차는 성능 블록 때와 같은 자리에서 나왔습니다.** 작업 7(`0x427ac0`)의 루프가
`[this+0x850] << 9` 에 `i × 56` 을 더해 오프셋을 만들고, 길이는 `0x38` 에 `cmove` 로
열 번째만 8 — 레이어 하나(512 B)를 10청크로 보냅니다. 순정은 레이어 0 일 때 공장
키맵을 밑에 깔고 DB 행을 얹어 512바이트를 **새로 만들어** 보내지만, 이 앱은 §4.5.6 과
같은 이유로 보드가 준 바이트를 고쳐 되돌려 보냅니다. 이 앱의 모델에는 61키분밖에 없고,
나머지를 0 으로 밀면 슬롯 0 의 타입 바이트까지 지워져 위 2번의 부팅 검사가 키맵을
통째로 되깔 수 있습니다.

**보드에서 동작했습니다.** 근거가 가장 얇았던 것이 라이브 키맵 읽기(`0x08`)였습니다 —
순정이 아예 보내지 않는 명령이라 베낄 호출 지점조차 없고, 핸들러가 `0x07` 의 것과
베이스만 다르다는 사실이 전부였습니다. 그 상태로 보내기 전에 가짜 보드 검사
(`tools/check/keymap-write.ts`)로 패킷 순서와 레코드 왕복을 먼저 고정해 두었고,
하드웨어에서 읽기·쓰기가 그대로 동작했습니다 (보드 소유자 확인, 2026-09-06).
검사는 그대로 둡니다 — 이제는 "맞기를 바라는 순서" 가 아니라 **동작하는 것으로 확인된
순서**라, 그걸 깨는 변경은 남의 키보드가 아니라 여기서 걸려야 합니다.

## 3. 실제로 효과가 있었던 방법

- **한 번에 한 변수.** DB 두 개 비교(§2.4)가 가장 값싸고 확실한 실험이었습니다.
- **불변량으로 필드 식별**(§2.5). 값을 해석하려 하지 말고, 무엇에 대해 변하지 않는지를
  묻는 것.
- **두 출처가 만나는 지점을 찾기.** 0.02 mm 는 DB 와 하드웨어 양쪽에서 독립적으로
  나왔습니다.
- **컴파일러 관용구 되읽기**(§2.3). `(x*8-x)<<3` 을 곱셈으로 복원한 게 블록 구조를
  열었습니다.
- **부정 결과를 적극적으로 받기.** 사용자의 "그 셋을 빼도 LED 가 바뀐다", "P키랑 /키가
  충돌한다", "이 8개는 인식이 안 된다" 가 각각 틀린 결론 하나씩을 죽였습니다.
  **긍정 확인보다 정보량이 많았습니다.**

| 17 | 필드 상한은 UI 취향 문제 | (설계 판단) | 5비트 데드존에 50카운트를 넣으면 `& 0x1f` = 18, 즉 0.36 mm 가 조용히 들어감 |
| 18 | 보정 상태는 보드 중앙값 대비 비율로 판정하면 된다 | 절대 문턱값을 모르니 상대값이 안전하다는 판단 | 사용자: "테두리가 바뀌지 않는다" — **전체가 나쁜 보드**에서 중앙값이 같이 내려가 61개 전부 "정상" |
| 20 | `0xaa` 가 응답하지 않는다 (펌웨어 미구현 의심) | 캘리브레이션 진입마다 뜨는 "보정 표를 읽지 못했습니다" | 와이어 로그 — 같은 밀리초에 나간 패킷이 둘이었고, 단독으로 보내니 **5 ms 만에** 답했다 |
| 21 | 초기화가 `0x20700` 에 키맵을, `0x20b00` 에 키별 성능을 쓴다 | 초기화 루틴의 복사 **순서**만 보고 대상 주소를 짝지음 | 각 주소를 읽는 **명령 핸들러**와 대조 — `0xa0`(성능)이 `0x20700`, `0x08`(키맵)이 `0x20b00` |
| 22 | `0x0a`(384 B)는 미할당 FN 레이어다 | 384 B = 128 × 3 이라 키맵과 같은 모양이고 전부 0 | LED 경로 `0x135f8` 이 `[key*3+0..2]` 를 **R/G/B 레지스터**에 싣는다 — 키별 커스텀 RGB |
| 23 | `0xa3` · `0xa5` · `0xa7` 이 전부 조명이다 | 순정에서 세 명령이 같은 조명 함수들에서 나감 | 키맵 타입 `0x90` 이 `0xa3` 의 영역을 `0x22100 + param*24` 로 인덱싱 (`0x88b6`) — **고급키 표** |

각각의 교훈:

**#16 — 관측에서 성질을 유도했는데, 관측 자체가 반쪽이었다.** 두 `0x06` 호출부가
겹치지 않는 범위를 수정한다는 것은 사실입니다. 거기서 "펌웨어가 필드를 독립적으로
취급한다" 를 유도했고, 그러면 한 바이트만 세운 희소한 블록을 보내도 안전하다는 결론이
따라옵니다. 그런데 **각 호출부가 전송 직전에 무엇을 하는지는 보지 않았습니다.** 둘 다
`0x05` 를 읽어 응답 65바이트를 쓰기 버퍼에 복사한 뒤 자기 범위만 고칩니다
(`0x42960a`–`0x42964d`, `0x428b13`–`0x428b93`). 희소한 블록을 보내는 코드는 순정
드라이버에 없으므로, 필드 독립성에 대한 증거는 **한 줄도 없었습니다.**

대가는 실제 버그였습니다. `enableAnalogReport()` 가 그 결론 위에 만들어져 있었고,
`payload[15]` 만 세운 블록을 보내 폴링 레이트 · 데드존 · 게임 잠금 · 절전 시간을 매번
0으로 덮고 있었습니다. 명세 §4.8.1.

> 교훈: 두 호출부의 **차이**를 봤다면 **공통점**도 봐야 합니다. 차이에서 유도한 성질은
> 공통점이 반증할 수 있습니다.

**#17 — "상한은 UI 문제" 가 아니었다.** 데드존 입력 상한을 1 mm 로 두고 넘어갔습니다.
필드는 5비트이고 인코더는 `& 0x1f` 로 마스크하고 있었으므로, 1.00 mm(50카운트)를 넣으면
18카운트 = **0.36 mm** 가 들어갑니다. 실패도, 경고도 없이 값이 접힙니다. 상한을 잘못
두는 것과 잘못된 값을 쓰는 것 사이에 UI 라는 완충재가 있다고 생각한 것이 착각이었습니다 —
인코더가 관대하면 UI 가 마지막 방어선이 됩니다.

지금은 `KEY_PERF_LIMITS` 한 곳에 근거와 함께 적혀 있고, 인코더는 마스크가 아니라
포화시키며, UI 상한이 같은 상수를 읽습니다. 세 곳이 어긋날 수 없게 만드는 것이 요점입니다.

**#18 — 상대 기준은 "전부 나쁜 경우" 를 원리적으로 볼 수 없다.** 절대 문턱값을 모르는
상태에서 보드 중앙값 대비 비율로 판정하기로 했습니다. 이웃보다 유독 안 움직이는 키를
잡는 데는 맞고, 스위치·자석이 달라도 성립하니 안전한 선택으로 보였습니다.

놓친 것은 **고장이 기준을 같이 움직인다**는 점입니다. 모든 키가 똑같이 나쁘면 중앙값도
같이 내려가고, 모든 키가 중앙값의 1.0 이 되어 61개 전부 "정상" 이 됩니다. 그리고 이건
드문 경우가 아닙니다 — 언어 문자열 1056 이 묘사하는 표준 시나리오, 펌웨어 업데이트
직후 키보드 전체가 빨강·노랑인 상태가 정확히 그것입니다. **제가 근거로 삼은 바로 그
문자열이 제 판정 방식이 못 보는 경우를 설명하고 있었습니다.**

검사도 이 구멍을 못 잡았습니다. "한 키만 나쁜 보드" 는 검사했는데 "전부 나쁜 보드" 를
검사하지 않았으니, **테스트가 구현과 같은 가정 위에 있었던 것**입니다.

지금은 절대 하한과 상대 비율을 같이 씁니다. 절대 하한은 표본이 필요 없어 첫 키부터
동작하고, 상대 비율은 하한이 한참 아래일 보드에서 이상치 하나를 잡습니다.

> 교훈: 기준을 데이터에서 뽑을 때는 **고장이 그 기준에 섞여 들어가는지**를 먼저
> 물어야 합니다. 중앙값·평균은 소수의 이상치에는 강하고 다수의 고장에는 무력합니다.

**#1 — 문자열은 의도가 아니다.** 이게 가장 비싼 오류였습니다. 제가 FEATURE 리포트라고
말한 탓에 캡처 시도가 엉뚱한 것을 찾고 있었을 가능성이 큽니다. 바이너리에 심볼이
있다는 건 링커가 넣었다는 뜻일 뿐입니다. **참조 횟수를 세야 합니다.**

**#2 — UI 문자열은 여러 모델이 공유한다.** 순정 드라이버 하나가 제품군 전체를
담당하므로, UI 에 있는 기능이 이 보드에 있다는 보장이 없습니다. 데이터가 우선입니다.

**#4 — 상관을 인과로 봤다.** 응답 시간이 긴 명령이 뭔가 무거운 일을 한다는 건 그럴듯한
추론이지만, 그럴듯함이 증거가 아닙니다. 그리고 진짜 이유가 밝혀졌을 때(§2.3) 그것은
개별 명령의 성질이 아니라 **모든 블록 쓰기 명령의 공통 성질**이었습니다. 즉 원인의
층위 자체를 잘못 짚고 있었습니다. 이 결과로 `SAFE_COMMANDS` 를 부작용이 관찰되지 않은
`0x01` / `0x02` / `0xa9` 세 개로 좁혔습니다.

**#5 — 표본 3개로 61개의 고유성을 주장했다.** Esc·A·Space 에서 `[12..13]` 이 서로
달랐다는 관측은 참이었지만, "그러므로 키별 고유" 는 표본 크기가 뒷받침하지 않는
일반화였습니다. 게다가 이 오류 위에 코드 버그가 하나 더 얹혀 있었습니다 — 이벤트 집계
맵의 키를 `sensorId` 로 잡아서, usage 가 정상인 P 와 `/` 까지 한 항목으로 합쳐졌습니다.
잘못된 모델과 잘못된 구현이 겹치면 증상이 원인을 가립니다.

**#6 — 부작용이 없다는 걸 확인한 게 아니라, 부작용이 안 보였을 뿐이다.** 아날로그
스트림이 "아무것도 켜지 않아도 그냥 올라온다" 고 적었습니다. 관측은 진짜였습니다 — 키를
누르면 이벤트가 올라왔습니다. 하지만 그 관측을 **순정 드라이버를 띄워 둔 채로** 했고,
드라이버가 성능 탭에서 1.9초마다 보드를 켜 주고 있었습니다. 내가 관측한 것은 보드의
기본 동작이 아니라 **다른 프로그램이 만들어 준 상태**였습니다. 정적 분석으로
`0x429f20` / `0x42cb80` 을 읽고서야 드러났습니다 (명세 §3.2).

> 교훈: "X 없이도 동작한다" 를 주장하려면 **X 를 실제로 없앤 상태에서** 봐야 합니다.
> 순정 드라이버를 완전히 종료하고, 보드를 뽑았다 꽂고, 그 다음에 관측할 것.

**#7 — 짝 중 어느 쪽이 켜기인지 정적 분석으로 정했다.** `0x429f20` 이 플래그로 `0xa9` /
`0xa8` 을 고르는 것까지는 정확히 읽었습니다. 거기서 "플래그 기본값(0)에서 나가는 쪽이
정상 경로이므로 `0xa9` 가 켜기" 라고 결론했는데 **반대였습니다** — `0xa8` 이 진입,
`0xa9` 가 해제입니다. 코드 구조는 두 명령이 **짝**이라는 것만 말해 주고, 어느 쪽이
어느 방향인지는 말해 주지 않습니다. 방향은 보드에 물어봐야 알 수 있었습니다.

> 이 오류에는 대가가 붙어 있었습니다. 잘못된 배정 위에서 "정지할 때 짝인 `0xa8` 을
> 보낸다" 는 정리 코드를 짰는데, 그것은 정지할 때마다 **캘리브레이션 모드로 들어가는**
> 코드였습니다. 방향을 틀리면 해제 경로가 진입 경로가 됩니다.

**#8 — 모드를 관찰 창구로 여겼다.** `0xa8` 을 "스트림을 켜는 스위치" 로만 봤습니다.
실제로는 키를 끝까지 누르면 **바닥 자성값을 보정하는** 모드였습니다. 즉 모니터를 켜고
키를 바닥까지 누르는 것은 읽기가 아니라 **쓰기**입니다. 드라이버가 이 모드에서만
1.9초마다 갱신을 보내는 이유도 그래야 설명됩니다.

**#9 — 안 변하는 값이라고 두 번 확인했지만, 변하는 조건을 안 만들어 봤다.**
`payload[12..13]` 을 "주소는 아니지만 키마다 고정" 으로 뒀습니다. 한 키의 모든 샘플에서
값이 같았고, 기준 ADC 도 그랬습니다. 관측은 반복까지 했으니 튼튼해 보였습니다.

빠진 것은 **그 값을 바꾸는 조작**이었습니다. 캘리브레이션을 돌리자 LCtrl 의 센서값이
`0x0805` → `0x0806` 으로 바뀌었고, 그 자리는 LAlt 의 것이어서 **LCtrl 이 LAlt 로
해석되었습니다**. 오해석은 미해석보다 나쁩니다 — 화면이 자신 있게 거짓을 말합니다.

> 교훈: "상수" 는 **관측 기간에 대한 진술**입니다. 상수라고 쓰려면 그것을 바꿀 만한
> 조작(보정·재부팅·펌웨어 갱신)을 한 번씩 해 보고 나서 써야 합니다. #6 과 같은 모양의
> 오류이고, 그때 얻은 교훈("X 를 실제로 없앤 상태에서 보라")을 다른 필드에는 적용하지
> 않았습니다.

**#10 — 정답지가 답을 가렸다.** 캘리브레이션에 흔들리지 않는 키 주소를 찾으려고, usage
로 이름을 말하는 키 53개를 정답지로 삼아 바이트마다 "한 키 안에서 고정 + 키마다 다름" 을
검사하는 도구를 만들었습니다. 논리는 맞았고, **답은 그 검사를 통과하지 못했습니다.**

`payload[2]` 는 일반 키에서 전부 같은 값입니다. 그러니 "키마다 다름" 에서 탈락하고
`중복` 으로 분류됩니다. 정작 그 바이트는 **수정자 8개에서만** 서로 다릅니다 — 찾던 것이
바로 그 8개였는데, 정답지에 그 8개가 없으니 보이지 않았습니다. 관측 데이터에는 처음부터
들어 있었고, 도구가 그것을 걸러냈습니다.

답은 결국 바이너리에서 나왔습니다 (`0x426050` 의 점프 테이블). 하드웨어 관측과 정적 분석
중 어느 쪽도 혼자서는 답을 못 줬습니다.

> 교훈: 분석 도구의 필터는 **가설**입니다. "주소라면 모든 키에서 달라야 한다" 는 가설이
> 참이라고 가정하고 필터를 걸었고, 실제 답은 "찾는 대상 안에서만 다르다" 였습니다.
> 후보를 지우는 도구를 만들 때는, 그 도구가 지운 것을 한 번은 봐야 합니다.

**#11 — 그럴듯한 원인을 찾자마자 원인이라고 불렀다.** "보정 전에는 감지가 안 된다" 를
듣고 `parseKeyEvent` 가 총 스트로크 0 인 이벤트를 버리는 코드를 발견했습니다. 보정 전
보드가 스트로크를 0 으로 보고한다면 증상이 정확히 설명되고, 실제로 그 코드는 버그였습니다.
**그래서 원인이라고 단정했고, 아니었습니다.** 고친 뒤에도 증상이 그대로였습니다.

진짜 원인은 `0x06` 의 플래그 바이트였습니다 (명세 §3.2). 두 개가 겹쳐 있었을 뿐입니다 —
버그 하나와 빠진 단계 하나.

> 교훈: 증상을 설명하는 버그를 찾았다는 것은 **그 버그가 원인이라는 증거가 아닙니다.**
> 특히 코드에서 찾은 버그는 언제나 그럴듯해 보입니다. 고친 다음 증상이 사라지는 것을
> 확인하기 전까지는 "원인 후보" 라고 불러야 합니다. #4 와 같은 오류(상관을 인과로)이고,
> 이번에는 내가 그것을 사용자에게 단정형으로 보고했습니다.

**#12 — 관측한 코드를 그대로 베끼면서, 그 코드가 어느 모드의 것인지 안 봤다.** 순정
드라이버가 `0xa8` 을 1.9초마다 재전송하는 것을 보고 "이 모드는 갱신하지 않으면 꺼진다" 로
읽고, 모니터에 1.5초 주기 재전송을 넣었습니다. 재전송 코드는 실재했고 주기도 정확했습니다.

놓친 것은 **그 코드에 걸린 조건**입니다. `0x42cb1a` 가 `[this+0x541fc] != 0` 을 요구하므로
그 루프는 **캘리브레이션 모드에서만** 돕니다. 일반 관찰에서는 `0xa8` 한 번이면 걸쇠처럼
유지됩니다. 조건문 한 줄을 기능이 아니라 배경으로 읽은 결과, 우리가 만든 모니터는:

- 켜는 동안 타이핑을 죽였고 (→ "모니터 실행 중 타이핑 불가" 를 **사양이라고 문서에 적었습니다**)
- 모니터링 내내 재보정을 돌려서 기준 ADC 와 센서값을 계속 움직였습니다

즉 오류 #8·#9 에서 "캘리브레이션이 식별자를 깨뜨린다" 며 관측했던 표류의 상당 부분은
**우리 코드가 만든 것**이었습니다. 남의 버그를 찾다가 자기 버그를 관측하고, 그것을 펌웨어의
성질로 기록했습니다.

> 교훈: 바이너리에서 베낀 동작에는 **그것이 실행되는 조건**까지 함께 베껴야 합니다.
> `if` 를 빼고 본문만 가져오면, 특수 모드의 동작이 기본 동작이 됩니다.

**#13 — 색인 가설 세 번 (슬롯 매핑).** 같은 증상 — "값은 그럴듯한데 키가 뒤죽박죽" — 이
세 번 다른 원인에서 나왔습니다. 세 번 다 해독된 표만 보면 그럴듯했고, 매번 **원본 슬롯
바이트**가 갈랐습니다.

| 시도 | 근거였던 것 | 어떻게 틀렸는지 드러났나 |
|---|---|---|
| `key_index` | XML 에 있는 값이고 16 단위 행 경계라 행렬 주소처럼 보였다 | 슬롯 ≥64 인 22개 키가 전부 0, 나머지는 다른 키 값 |
| 레이아웃 순서 (0–60) | XML 파서가 `key_index` 를 버린다는 발견 + 61키 = 61슬롯 | 덤프에 슬롯이 **3칸 비어** 있었다 (12·20·53). 순서 가설로는 설명 불가 |
| `0x0a` 를 키맵으로 읽기 | 크기(384 = 128×3)와 인코더 형식이 맞았다 | 응답이 **전부 0**. 맵의 출처는 `0x07` |

첫 번째는 특히 비쌉니다. `key_index` 를 "펌웨어 키 주소" 라고 **명세에 단정형으로**
적어 뒀고(§6 구판), 그 문장이 코드로 옮겨졌습니다. 실제로는 순정 드라이버가 그 값을
파싱해서 **버립니다** — atoi 결과가 저장되지 않고 다음 줄에서 덮어써집니다. 그리고 그
속성 이름 문자열은 바이너리 전체에서 그 한 곳에서만 참조됩니다. 즉 **오류 #1 과 같은
모양**입니다: 문자열이 있다는 것과 쓰인다는 것은 다릅니다. #1 에서 "참조 횟수를 세야
한다" 는 교훈을 얻었는데, 데이터 파일의 필드에는 적용하지 않았습니다.

두 번째는 부정 증거를 과대해석했습니다. "`key_index` 가 아니다" 가 참이라고 해서
"그러면 순서다" 가 따라오지 않는데, 후보가 두 개뿐인 것처럼 생각했습니다. 실제 답은
세 번째 후보(하드웨어 배선)였고, 그건 **어떤 계산으로도 나오지 않습니다.**

> 교훈 하나: **색인 가설은 원본 바이트 없이 검증되지 않습니다.** 해독된 값이 그럴듯한
> 것은 아무 증거가 아닙니다 — 8바이트 레코드는 어느 슬롯에서 읽어도 그럴듯하게
> 해독됩니다. 그래서 덤프 UI(128슬롯 × 원본 바이트 + 해독값 + 키 이름)를 남겨 뒀고,
> 폴백 매핑을 쓸 때 화면에 "추정값" 을 띄웁니다. 조용히 틀리는 것이 최악입니다.
>
> 교훈 둘: **"계산할 수 없다" 도 결론입니다.** 매핑을 레이아웃에서 유도하려는 시도를
> 세 번 하고 나서야, 순정 드라이버도 유도하지 않는다는 것을 확인했습니다 —
> `슬롯 → usage` 맵을 키맵 블록에서 만듭니다. 정적 테이블 전수 검색까지 해서
> (실측 행 제약으로 61칸 중 30칸 이상 맞는 창이 **0개**) 없다는 것을 확인한 뒤에야
> "보드에서 받는다" 로 갔습니다. 그 검색을 먼저 했으면 두 번을 아꼈습니다.

**#14 — 가변인자 push 순서를 UI 순서라고 읽었다 (스위치 이름).** 스위치 종류 8종의
이름을 언어 문자열 1450–1457 의 push 순서(`0x44af0d`–`0x44aff8`)로 배정했습니다.
C 는 가변인자를 역순으로 push 하니 첫 인자는 마지막 push, 그래서 목록은 1450부터 —
논리는 맞습니다. **하드웨어에서 8개 중 4개가 어긋났습니다** (0↔4, 1↔3 형태).

즉 그 가변인자 목록이 콤보박스의 최종 순서가 아니었습니다. 어디서 재배열되는지는 아직
못 찾았습니다. 코드 구조는 "이 8개가 한 목록이다" 까지만 말해 주고, **순서**는 말해
주지 않았습니다.

> 교훈: #7 과 같은 오류입니다. 그때는 "두 명령이 짝이다" 는 맞았지만 **어느 쪽이 켜기인지**
> 는 보드만 알았습니다. 이번엔 "이 8개가 목록이다" 는 맞았지만 **순서**는 보드만
> 알았습니다. 바이너리는 구조를 주고, 방향·순서·의미는 하드웨어가 줍니다.

**#15 — 실패 모드를 조용하게 설계할 뻔했다.** 슬롯 매핑을 키맵에서 받도록 고칠 때,
읽기가 실패하면 추정 매핑으로 내려가게 했습니다. 그 자체는 맞는 설계인데, 처음에는
**내려간 사실을 화면에 표시하지 않았습니다.** `0x0a` 가 전부 0을 돌려주자 앱은 조용히
추정 매핑으로 61키를 그렸고, 사용자는 "매핑이 아직 안 맞는다" 만 볼 수 있었습니다 —
왜 안 맞는지는 덤프에 찍힌 `00 00 00` 을 보고서야 알았습니다.

> 교훈: 폴백은 **눈에 보여야** 폴백입니다. 지금은 "보드 키맵 기준 / 추정값" 을 배지로
> 띄우고, 해석된 키 수(61/61)를 같이 보여 줍니다. 덤프에도 `slot map: keymap|fallback`
> 한 줄이 들어갑니다.

**#19 — 순정 드라이버가 보정 상태를 계산한다고 결론지었다. 계산하지 않습니다.**
가장 오래 붙들고 있던 오류이고, 잡히는 데 새 출처가 하나 필요했습니다.

증거는 좋았습니다. `mui.dll` 이 키별로 ADC 진폭의 **누적 최댓값**을 들고 있고
(`0x1005ebbb` 의 `cmovg`), 나머지 세 필드는 전부 덮어쓰기입니다. 언어 문자열 1056 은
"각 키들이 녹색이 될 때까지 반복해서 키들을 누르세요" 라고 합니다. 반복하면 좋아지는
판정은 누적 최댓값이다 — 두 출처가 맞물렸고, §3 처럼 교차검증된 결론은 그때까지 하나도
틀린 적이 없었습니다.

그런데 **문턱값이 아무리 찾아도 안 나왔습니다.** `[0x74]` 를 상수와 비교하는 코드가
`mui.dll` 어디에도 없었습니다. 그걸 "그리기 경로 안에 숨어 있다" 로 처리하고 이 프로젝트
나름의 상대 판정(보드 중앙값 대비 비율)을 얹었습니다.

없었던 것입니다. **판정은 순정 드라이버 안에서 일어나지 않습니다.** 펌웨어가 키별로
상태 바이트를 들고 있고 (§3.3), 그것을 **아날로그 이벤트의 `payload[10]` 으로 그냥
보냅니다.** 순정 드라이버는 그 바이트를 받아서 색으로 옮길 뿐이라, 문턱값이 있을 자리가
애초에 없었습니다. 같은 이벤트의 `payload[11..13]` 도 "센서값" 이 아니라 **보정 계수의
10진 세 자리**였습니다 — 순정이 `"%d%d%d"` 로 이어 붙이는 이유가 그것입니다.

세 가지가 이 오류의 산물로 남았습니다:

1. **`payload[10]` 을 `check_count` 라고 적었던 것.** 순정의 디버그 포맷 문자열에서 온
   이름이고, 펌웨어는 거기에 아무것도 세지 않습니다.
2. **`payload[12..13]` 로 만든 지문.** 그것이 왜 보정 후에 바뀌는지 (§3.2 "센서값도
   바뀐다") 설명이 없었는데, 보정 계수의 소수 두 자리이므로 **보정이 잘 될수록 바뀌는 게
   정상**입니다. LCtrl 이 `0x0805` → `0x0806` 이 된 것은 계수가 0.85 → 0.86 이 된 것입니다.
3. **중앙값 대비 상대 판정 전체.** 실제 신호(계수)를 못 봤기 때문에 대리 지표를 만들어야
   했고, 그 대리 지표의 문턱값은 끝까지 근거가 없었습니다.

> 교훈 하나: **찾는 상수가 안 나오는 것은 그 자체로 증거입니다.** "숨어 있겠지" 로
> 넘기지 말고 "여기서 계산하지 않는 것 아닌가" 를 먼저 의심해야 했습니다.
>
> 교훈 둘: 이 프로젝트는 세 출처(§0)로 버텨 왔는데, **네 번째가 내내 있었습니다** —
> 펌웨어 자체입니다. 순정 업데이터 exe 안에 리소스로 들어 있고, 추론 없이 규칙을 그냥
> 읽을 수 있습니다. 드라이버는 보드가 무엇을 받는지 알려주지만, 보드가 그것으로 **무엇을
> 하는지**는 펌웨어만 압니다.

**패턴:** 16개가 **단일 증거로 내린 결론**입니다. 교차검증이 대부분을 막아 주었지만
**#19 가 그 규칙을 깼습니다** — 디스어셈블과 언어 리소스가 서로를 확인해 줬는데도
틀렸고, 두 출처가 같은 층(순정 드라이버)에 있었기 때문입니다. 그 층에서는 보이지 않는
답이었습니다. 교차검증은 출처가 **다른 층**일 때만 값을 합니다.

#6 은 여기에 한 겹을 더합니다 — 관측이 정확해도 **관측 환경이 결론의 일부**입니다.
#7 · #8 · #14 는 또 한 겹입니다: 바이너리는
**구조**를 정확히 알려주지만 (두 명령이 짝이다, 주기가 1.9초다, 이 8개가 한 목록이다),
그 구조에 **어느 방향** · **어떤 순서** · **어떤 의미**가 붙는지는 알려주지 않습니다.
방향과 순서와 의미는 보드만 압니다.

#13 은 마지막 겹입니다: **주소 체계는 계산할 수 있는 것이 아닐 수도 있습니다.** 세 번의
색인 가설이 모두 "레이아웃 파일에서 유도한다" 는 전제를 공유했고, 답은 하드웨어 배선이라
어떤 유도로도 나오지 않았습니다. 순정 드라이버도 유도하지 않고 보드에 물어봅니다.

#19 는 그 다음 겹입니다: **답이 어느 층에도 없으면 층을 하나 더 열어야 합니다.** 세
출처(§0)가 전부 순정 소프트웨어와 보드의 겉모습이었고, 규칙 자체는 펌웨어 안에
있었습니다. 펌웨어는 처음부터 손에 있었습니다 — 순정 업데이터 exe 안에서.

**#20 — 우리 코드의 버그를 보드의 성질로 읽었다.** `0xaa` 는 순정 드라이버가 보내지
않는 명령이라 펌웨어에서만 근거를 얻었고 (명세 §3.3), 그래서 "펌웨어에서만 확인된
명령이 하드웨어에서 안 되는구나" 가 아주 그럴듯한 이야기였습니다. **경고 문구가 그
이야기를 반증할 수 없게 만들었습니다** — "보정 표를 읽지 못했습니다 (명령 0xaa)" 는
실패한 명령의 이름만 있고 실패한 *이유*가 없는 문장이고, 그 이유는 `catch {}` 에서
버려지고 있었습니다. 이름만 있는 에러는 이름이 붙은 쪽을 범인으로 읽히게 합니다.

로그는 다르게 말했습니다. `0xaa` 와 키맵의 `0x01` 이 **같은 밀리초에** 나갔고 보드는
나중 것만 답했습니다. 원인은 `useCalibrationRun` 의 `Promise.all` — 서로를 모르는 두
멀티패킷 읽기를 동시에 던진 것이고, 보드는 HID 패킷 버퍼가 하나입니다. 같은 300 ms
동안 키맵 청크 14개가 전부 성공했다는 사실이 "보드가 바쁘다" 는 대안 설명도
지웠습니다. 단독으로 보내자 5 ms 만에 답했고, 돌아온 레코드는 펌웨어에서 유도한
레이아웃과 **바이트 단위로** 맞았습니다.

교훈 세 가지입니다:

1. **실패 사유를 버리지 마십시오.** 삼켜진 예외 하나 때문에 와이어 캡처가 필요했습니다.
   지금은 사유가 경고에 같이 표시됩니다 (`src/features/Calibration.tsx`).
2. **이름을 말할 거면 이유도 말하십시오.** 실패한 명령만 적힌 경고는 진단처럼
   보이지만 진단이 아니고, 읽는 사람을 틀린 방향으로 밉니다.
3. **동시성은 프로토콜의 일부입니다.** 명세 어디에도 "한 번에 하나" 라고 쓰여 있지
   않았지만, 버퍼가 하나인 장치에서 그것은 프레임이나 체크섬만큼 강한 제약입니다.
   `HidLink` 가 모든 쓰기를 직렬화하고 (`src/hid/link.ts`), 가짜 보드로 검사합니다
   (`tools/check/link-queue.ts`).

**#21 · #22 · #23 은 한 묶음입니다: 블롭의 정체를 그 블롭의 *모양*으로 추측했습니다.**
384바이트 3바이트 레코드라서 키맵으로 읽었고(#22), 초기화가 그 순서로 복사해서 그
순서로 짝지었고(#21), 순정이 조명 화면에서 보내니까 조명이라고 적었습니다(#23).
셋 다 그럴듯했고 셋 다 틀렸습니다.

세 번 다 같은 것이 잡았습니다: **그 바이트를 실제로 소비하는 코드.** RGB 는 LED 경로가
R/G/B 레지스터에 싣는 것으로, 고급키는 키맵 레코드가 24바이트 단위로 인덱싱하는 것으로,
주소 짝은 그 주소를 읽는 명령 핸들러로 갈렸습니다. 블롭이 어떻게 생겼는지는 그것이
무엇인지 말해 주지 않고, **누가 그것을 읽는지가 말해 줍니다.**

#22 는 대가도 있었습니다. `0x0a` 를 "전부 0인 미할당 레이어" 로 읽은 것이 슬롯 매핑
첫 시도를 추정 경로로 보냈고, 그때는 보드가 이상한 줄 알았습니다. 전부 0인 것은 정상
이었습니다 — 커스텀 색을 안 쓴 것뿐이었습니다.

## 5. 남은 것 — 그리고 각각을 가르는 실험

명세 §9 의 목록에, **무엇을 하면 갈리는지**를 붙입니다.

| 미해결 | 결정적 실험 | 비용 |
|--------|-------------|------|
| ~~`0xa1` 쓰기가 실제로 먹히는가~~ | **끝났습니다** — 액추에이션 쓰기를 하드웨어에서 확인했습니다 | — |
| `0x06` 쓰기가 실제로 먹히는가 | 바닥까지 트리거를 켜고 다시 읽는다. 같은 대조 경로 (§4.8.1) | 실험 1회 |

| 슬롯 12 / 20 / 53 이 왜 비는가 | 스위치를 하나 빼고 `0xa0` 을 읽어 해당 슬롯이 0이 되는지 본다 | 실험 1회 |
| 성능 블록 슬롯 126 / 127 의 정체 | 순정에서 한계값(액추에이션 최대 등)을 바꿔 이 레코드가 따라가는지 본다 | 실험 1회 |

| 스위치 이름 순서를 순정이 어디서 재배열하는가 | 콤보박스 채우기 호출부(`0x44a160`)를 끝까지 따라간다 | 정적 분석 |

| `[12..13]` 의 정체 | 캘리브레이션 전후로 값이 바뀌는지 본다 | ⚠ 식별표가 어긋남 |
| ~~`0x08` 의 내용~~ | **끝났습니다** — 실사용 키맵입니다 (명세 §3.8) | — |
| `0x0d`(매크로) 본문 레코드의 필드 | 순정에서 매크로를 하나 녹화하고 `0x0c` 로 읽어 대조 | 실험 1회 |
| 고급키 24바이트 레코드의 필드 | §2.7 의 신호 기법 — DKS 하나를 심고 `0xa2` 로 읽는다 | 실험 1회 |
| 레이어 동작 `0x04` 가 실제로 먹히는가 | 키맵 슬롯에 `f0 04 00` 을 쓰고 눌러 LED 3회 점멸과 `0x05`의 `payload[9]` 를 본다 | 실험 1회, ⚠ `0x05` 동작은 금지 (명세 §7.1) |

`[12..13]` 실험은 성공해도 부작용이 있습니다. 재캘리브레이션은 기준 ADC 를 바꾸므로
`fingerprints.ts` 의 8개 항목이 어긋나고, 이벤트 탭에서 다시 연결해야 합니다.
급하지 않은 질문이라 미뤄 두는 게 맞습니다.

### 5.1 쓰기 검증 — 읽기 채널이 생겼고, 그래서 쓰기를 붙였다

> **갱신 3.** 이 절은 세 번 갱신되었습니다. 처음에는 "읽어서 확인할 채널이 없다" 를
> 전제로 쓰였고, 읽기 명령이 발견되면서 그 전제가 깨졌습니다. 그 다음 쓰기가 구현됐고
> (명세 §4.5.5, §4.5.6), 이제 **액추에이션 쓰기는 하드웨어에서 확인됐습니다.**
> 남은 것은 §5 표의 두 줄입니다 — 전역 블록(`0x06`)과 `0x02` 의 역할.

**쓰기 검증은 쓰고-다시-읽기로 끝납니다.** 코덱의 `writeKeyPerfConfigs()` 가 그 자리에서
합니다: 쓰기 전 블록을 읽고, 바뀐 슬롯만 갈아끼워 19청크를 보내고, **다시 읽어 바이트를
대조**합니다. 어긋난 슬롯은 `기록한 값 → 읽힌 값` 으로 화면에 그대로 나옵니다.

이 대조가 없으면 안 되는 이유는 프레임 때문입니다. 쓰기 응답은 **요청 에코**입니다
(명세 §3.1) — 펌웨어가 값을 받아 버리고 무시해도 응답은 똑같이 `0xaa` 로 돌아옵니다.
응답만 보는 쓰기는 성공과 실패를 구별할 수 없습니다.

**위험은 배치가 아니라 "쓰지 않은 바이트"였습니다.** `0xa1` 은 1024바이트 전체 교체이고,
순정 드라이버는 스테이징 버퍼를 0으로 밀고 자기가 아는 슬롯만 채웁니다 (`0x42c44b`).
이 앱이 같은 방식을 쓰면, 아직 모르는 것들이 전부 0으로 나갑니다 — 슬롯 126·127
(§4.5.4), 쓰이지 않는 채널 3개, `rec[0]` 상위 3비트 (§4.5.2), `ff ff ff ff` 미설정 표식
(§4.5.3). **그래서 읽기-수정-쓰기입니다.** 방금 읽은 블록을 고치면 모르는 것은 건드릴
수 없습니다.

같은 이유로 `switch_type` 도 보드에서 가져옵니다. 공장 기본값 `KeyConfig` 에는
`switch_type` 이 없어서(모델은 mm 단위 사용자 설정만 담습니다) 그대로 쓰면 스위치 종류가
0번으로 선언됩니다. `fromKeyConfig(config, current)` 의 두 번째 인자가 이 구멍을 막고,
UI 는 읽기 전에 쓰기 버튼을 잠급니다.

`tools/check/perf-write.ts` (`npm run check`) 가 가짜 보드로 이 성질들을 검사합니다.
검사를 처음 썼을 때 가짜 보드가 `KeyDef.usage` — **없는 필드** — 를 읽어 키맵을 전부
0으로 만들었고, 슬롯 매핑이 조용히 폴백으로 떨어졌는데도 **모든 단정이 통과했습니다**.
폴백 배치가 우연히 검사가 기대한 배치와 같았기 때문입니다. 오류 #15 가 검사 코드
안에서 재현된 것이라, 이제 맨 앞에서 "가짜 키맵이 61키 전부를 해석하는가" 를 먼저
확인합니다.

**액추에이션은 확인됐습니다.** 래피드 트리거는 같은 명령, 같은 8바이트 레코드의 다른
필드이므로 경로는 이미 검증된 것과 같습니다 — 새로 위험한 것은 필드 조합 쪽이고, 그건
§4.5.1 의 세 상태(`key_mode` 0/1/2)와 "분리" 접힘, 그리고 5비트·9비트 포화로 좁혀집니다.
`tools/check/rt-write.ts` 가 그 조합을 검사합니다.

전역 블록(`0x06`)은 별개입니다 — 명령도 다르고, 블록에 다른 화면의 설정이 같이 들어
있어 잘못 쓰면 폴링 레이트나 절전 시간이 함께 바뀝니다. 오류 #16 이 정확히 그 사고였고,
지금은 순정과 같은 읽기-수정-쓰기입니다. 실제 장치 확인은 아직입니다.

<details>
<summary>읽기 채널이 없던 시절의 우회로 (기록)</summary>

**액추에이션 포인트는 관측 가능합니다.**

보드는 아날로그 이벤트를 올려보내면서 **동시에 평범한 HID 키보드로도 동작합니다.**
그러니 키를 아주 천천히 누르면서 브라우저에서 두 가지를 같이 기록할 수 있습니다.

1. 아날로그 이벤트의 `[7]` — 0.02 mm 단위 실제 깊이, 연속적으로
2. `keydown` 이 발생한 순간

**`keydown` 이 뜬 시점의 `[7]` 값이 그 키의 실효 액추에이션 포인트입니다.** 정밀도는
이벤트 샘플 간격만큼입니다. 즉 캡처 장비 없이, 보드 스스로가 자기 설정을 읽어주는
**오라클**이 생깁니다.

블록 읽기가 더 직접적이고 정밀하므로 실제로 쓰이지는 않았습니다. 다만 이 오라클은
블록 읽기가 답하지 못하는 것을 답합니다 — **보드가 그 설정을 실제로 지키는가.**
바이트 대조는 값이 저장됐다는 것까지만 보증합니다.

⚠ 어느 쪽이든 규율은 그대로입니다.

- 한 번에 **명령 하나, 오프셋 하나**만 건드린다
- 조명 블롭 근처를 피한다 (오류 #4 로 이미 한 번 덮어썼습니다)
- 시작 전에 순정 드라이버로 프로파일을 저장해 **복구 경로를 확보**한다
- 순정 드라이버에서 조명 프로파일을 다시 적용하면 LED 는 복구됩니다
